| 原发现 | 已落地的行为 | 验收依据 |
|---|---|---|
| 1 · 对象错配 | 仪器操作步骤须绑定回执中的设备 ID，可进一步绑定通道、动作和采样窗口。不同子结果可分别支持各自的通道。串口和通用助手登记原始调用参数与宿主回执，核对时以回执中的实际身份优先。 | 单回执重复认领两台设备被拒绝，同一回执中分别成功的两个通道可通过，失败通道不能认领。 |
| 2 · 长任务和重启 | 已完成步骤保存独立的摘要凭据。原始大结果仍受缓存预算限制。最终回答可引用已核验步骤的凭据。恢复时将历史引用放入独立编号空间，可重验的报告重新校验，数值计算保留结果，既往设备操作标为需读回。 | 增加 110 条新观察后原计划仍可更新；重开后能读取带历史标记的原凭据；替换同一来源的版本会使原步骤重新待验。 |
| 3 · 错误结论和报告意图 | 工具失败无法支撑肯定结论。计划支持标记观测、推断、待证假设和缺少观测。识别写成、导出或保存 Markdown 文件的请求，支持撤销该要求。 | 原失败读取探针被拒绝；两种保存报告表述均产生文件目标；取消语句可移除目标。 |
| 4 · 整表核验 | 两个入口通过现有的 `report.read` 使用本地 `scan`。指定列名、数值上下界及分隔符，返回覆盖行数、有效数、无效数、越限数及行号。续扫绑定来源、规则、位置及累计计数。大父报告按 Markdown 块查找实际链接。 | 超过 32 MiB、16,384 条数据的 CSV 中定位到第 8,193 和第 16,385 行。单次全扫和分批续扫计数一致，非数值单列。超过 4 MiB 的父文档可引用末尾附件，代码块中的伪链接被拒绝。 |

| 6 · 工件恢复 | 整份报告先写入临时目录，生成包含相对文件名、大小、类型和 SHA-256 的清单后整目录发布。任务日志单独保存清单摘要。两个入口均在后台核验，显示缺失或改动的文件；旧报告只标记已核验正文。 | 移动完整报告目录后通过核验；改名、改写附件或改写正文均无法恢复为完整已核验工件。 |
| 评测成本 | 离线评测运行器为每个任务提供请求级记账文件，WiParse 在发送请求前登记请求 ID，在取得提供方用量后补记。重复读取同一请求去重，重试按新请求计费。统计附带任务和已接入请求的用量覆盖率。 | 实际启动的合成子进程分别以非零状态和超时退出，退出前已记录的 23 个 Token 在两种情况下均保留。未报告的用量保持未知。 |

例如检查 CSV 附件中的输入电压，可调用 `report.read`：

```json
{"attachment":"measurements.csv","scan":{"column":"VIN [V]","min":4.75,"max":5.25}}
```

这里的电压范围仅用于说明参数。实际任务使用产品规定的限值和 CSV 原列单位。返回 `next_cursor` 时，将其填入同一规则的 `scan.cursor`。完整覆盖且所有有效行落在限值内、无无效行时，才会给出整表范围内通过。异常样本有数量上限，累计计数覆盖全部已扫描记录。

## 评审结论

WiParse 已能把一次工程提问落到真实的软件操作：读取整份日志、回到命中行、提取点列、打开数据分析页、查询解码帧、等待仪器作业并保存带附件的报告。相较 1.2.3 和已提交的 1.2.4，本轮工作树尤其改善了断线后重复派发、报告读取边界和两个入口处理异步回执的一致性。[1.2.4 基线评审](engineering-agent-1.2.4.md) · [上一轮整改与验收](codex-agent-architecture-wiparse-1.2.4.md)

**当前首要差距是任务完成判定。** 本次在当前源码上复现，一份仪器回执可以让两个不同设备的操作步骤都显示完成；一次失败读取也能支持标题为“验证所有行均通过”的一般分析步骤。相反，长任务中的有效旧证据被淘汰后，连维持先前完成状态也可能失败。工程师看到的同一个“完成”因此可能过早出现，也可能在后续更新时失去依据。

**建议定位。** 当前版本适合工程师在场的辅助分析、回放和受控设备操作。要评价其能否独立交付硬件诊断，优先验证指定对象是否真的检测、结论能否从工件复核、测不到时是否正确保留未知。当前材料不足以计算相对 Codex 的真实任务胜率、Token 节省比例或现场故障召回率。

## 影响交付的具体发现

### 1. 高优先级 · 步骤完成有证据类型检查，缺少目标对象检查

**本次复现。** 仅登记一份设备 1、作业 7 的成功 `instrument.command` 回执。提交两个 `operation` 步骤，标题分别为“Scope A single”和“Scope B single”，均引用该回执。工作流返回接受，未完成目标为空。复现只调用工作流，现场没有执行第二台设备，也没有观察到模型自行发出该错误计划。设备防重复派发解决的是另一件事，两项检查都需要保留。[完成判据及计划更新](../../crates/wiparse-core/src/ai/workflow.rs)

**影响与修复。** 双示波器、双通道、多个充电轮次最易受影响。为具体步骤登记目标设备、通道、来源、时间窗、动作及所需观测层级。允许同一份回执支持它实际包含的多项结果。验收应同时覆盖“一份回执含 A、B 两个真实结果”与“仅含 A 却宣称 B 已完成”。

### 2. 高优先级 · 证据淘汰会破坏长任务中的已完成计划

**本次复现。** 上述计划第一次更新成功。再登记 48 条小型 `page.inspect` 观察，原样提交同一计划，返回 `AGENT.PLAN_UNKNOWN_OR_FAILED_EVIDENCE`。缓存上限为 48 条或 8 MiB，更新时会重新查找所有完成步骤引用的证据。这个缺口在小型、单次成功的回归中很难暴露。[证据留存和计划验证](../../crates/wiparse-core/src/ai/workflow.rs)

**修复与验收。** 将完成凭据与面向模型的近期缓存分开保存。最小凭据包含来源版本、目标身份、指标、单位、判据和可重验的工件摘要。用跨 100 条观察、关闭重开和来源替换三种情形验收。前两种应能复核旧步骤，来源改变时应明确标记需重验，硬件写动作不得因恢复被重发。

### 3. 高优先级 · 无法取证和已证实结论可能显示为同一种“完成”

**本次复现。** 仅登记 `report.read` 失败回执，提交标题为“Verify all rows passed”的 `analysis` 完成步骤，宿主接受。失败回执确实能证明“未取得报告”；它无法证明任何一行通过。另测“生成报告”触发宿主的报告文件目标，而“把这次充电分析写成一份可打开的 Markdown 文件”没有触发独立目标。后一种表达仍可能由模型正确建计划，但宿主少了一次兜底检查。[目标提取和证据规则](../../crates/wiparse-core/src/ai/workflow.rs)

**修复与验收。** 对“已观测结果”“已解释阻塞”“仅列出假设”使用不同终态。模型先给出结构化交付要求，宿主检查方法是否能支持该类结论。失败读回可完成阻塞说明，不能支持肯定判定。用同义表达、否定、更正以及“数据缺失但希望生成报告”的组合验收，避免新增一轮用户确认。

### 4. 高优先级 · 大报告连续可读，整表检查仍可能耗尽模型轮次

**核对与推算。** 现有回归从头读到大于 32 MiB 的 CSV 末尾，共 16,384 行。本次按相同夹具、每页 80 行请求和 32 KiB 序列化行预算复算，实际需 **1,093 页**。续页游标依赖前页返回值。共享助手默认 16 个模型轮次，可选最高 32 轮。仅靠模型逐次请求下一页，一次任务无法覆盖这份附件。1,093 是该夹具的页数估算，并非在线请求实测。另有独立限制：读取 Markdown 链接的附件时，父报告超过 4 MiB 会在链接检查阶段被拒绝。[分页与夹具](../../crates/wiparse-gui/src/test_report/ai_read/paging.rs) · [任务预算](../../crates/wiparse-gui/src/ai/agent.rs) · [附件入口](../../crates/wiparse-gui/src/test_report/ai_read.rs)

**修复与验收。** 对“核查全表是否越限”优先使用宿主本地聚合和区间覆盖记录，将规则、分母、异常行定位和未覆盖区间返回模型。逐页接口继续服务于抽查。验收在中段和末行分别植入异常，要求一次提问得到正确计数和来源；提前取消时只报告实际覆盖范围。对超过 4 MiB 的父报告单独验证附件链接解析。

### 5. 高优先级 · 工位读回与跨时钟归因仍有物理证据缺口

**源码结论。** 未决命令记录按厂家、型号、设备序列号或资源地址以及规范化命令生成键，迟到回执有会话和作业号约束。界面允许操作员读回后确认；解除记录本身没有独立测量值。跨时钟工具可用当前任务的两个锚点与给定误差找出返回页内候选帧，并明确输出同步及因果关系未经物理验证。示例无线充电工位仍标记 `UNCOMMISSIONED`。[命令登记](../../crates/wiparse-gui/src/instrument_control/agent_commands.rs) · [时钟对齐](../../crates/wiparse-core/src/ai/workflow.rs) · [工位配置](../../test-tools/plugins/wireless-charge-validation/station.json)

**修复与验收。** 按设备能力分别保存驱动结果、寄存器或状态回读、独立仪器测值和容差。涉及断充归因时，同时记录时钟域、锚点来源、误差区间和候选帧页的覆盖。用已知时差、相邻双帧、丢锚点、USB 断线与设备替换验收。同步不足时返回候选或未知，正式产品判定仍由工位规则产生。

### 6. 中优先级 · 报告恢复对正文与附件的保证不同

报告生成器会写 Markdown、证据 JSON，并按任务附 CSV、PNG 或逐点索引。恢复链使用保存的 SHA-256 核对 `report.md`；在该路径中未见对全部链接工件逐个比对原始摘要。因此，先前生成的报告正文可通过校验，但引用的数据附件可能已移动或改变。这是静态路径分析，本次未改动用户报告以模拟损坏。[工件生成](../../crates/wiparse-gui/src/ai/artifact.rs) · [恢复校验](../../crates/wiparse-gui/src/ai/journal.rs)

建议生成按相对路径记录的工件清单，列明类型、大小和内容摘要。恢复时显示“正文已核验、曲线 CSV 缺失”等逐件状态。验收分别只修改正文、附件、文件名，另测整个项目移至另一台机器后仍可核验。

**对测设计。** 沿用前期规划的 60 个独立实采任务，按采集批次隔离开发集与留出集。覆盖串口断充、协议时窗、死区、适配器兼容性、异常报表和跨设备恢复，并包含容易正确算出“未知”的反例。先以相同模型及工具做框架对照，再用实际部署的 DeepSeek、千问等提供方评估产品体验；若模型无法对齐，则标注为整体产品比较。两个 Agent 读取同一采集快照，设备写操作通过隔离工位或一致的回放，防止前一轮改变后一轮的输入条件。[原验收规划](engineering-agent-candidate-2026-11-11.md)

评审人员先盲查原始文件、波形索引及交付工件，再揭盲。危险误操作、缺测误判通过、凭据引用到错误设备应单列；每次正确交付成本用该组所有尝试的 Token 总数除以正确交付数。缺失用量须报告覆盖率，可核算子集另列。Codex App Server 可先作为只读评测组接入现有工具；在取得配对结果之前，保留当前 Rust 设备执行与本地分析路径。[运行器](../../scripts/run-engineering-benchmark.py) · [配对统计](../../scripts/compare-engineering-agent.py)
