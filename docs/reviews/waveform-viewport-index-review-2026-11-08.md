# 大波形视口索引优化：架构、影响与验证

更新：2026-11-08。用户测试包为已冻结的 **R20**；本报告描述打包完成后继续开发的 **R21 源码候选**，没有替换 R20 ZIP。

## 原因与调整

原视口查询按时间范围定位采样点后，对每一个显示桶逐点求极值。一次全景查询会重新扫描整个通道；平移、缩放、叠加重复触发时，即使前端已经放弃旧请求，后台仍可能完成这些扫描。这是重复 CPU 工作的来源，不能据此认定已经发现线程泄漏或原 Windows 崩溃的根因。

新方案在后台加载文件时，为每个不可变采样数组构建一次精确极值索引：每 256 点为一个块，整块的最小/最大值存入迭代式线段树。查询只扫描桶两端的零散采样点，完整块由索引合并。没有抽掉尖峰、平均化波形或降低原始采样精度。

原始数组及索引使用 Arc 共享。文件追加、关闭和快照克隆保持通道与索引同序，避免复制大数组；原子文件提交、请求代际和文件关闭互锁沿用既有路径。索引在文件加载工作线程中构建，不放到 GUI 线程。

## 改动范围与兼容性

仅修改新 GUI 的三个原生源文件：`src-tauri/src/wave_extrema.rs`、`wave_view.rs` 和模块注册 `main.rs`。

- 视口 API 的字段、采样点计数、时间边界、桶数量及桶内精确极值保持一致。
- 原始数组没有被修改；测量、协议解码和 CSV/ISF/WFM 导出继续读取原始采样值。
- 64 MiB 单文件及整个波形库的 16 文件、32 通道、3200 万点限制保持不变。
- 前端交互、旧兼容宿主、设备驱动、串口、测试运行器、插件和 MCP 的源码及既有产物未变；哈希复用边界记录在候选验证中。
- 代价是后台加载时增加一次索引构建，以及少量常驻索引数组。不是零成本优化，也没有据此扩大原容量限制。

索引构建为 O(N)，空间为 O(N/256)；单次视口查询主要为显示桶的两端扫描和整块查询，不再按全通道 N 点重新遍历。

## 实测结果

样本为用户提供的 `Normal.isf`，共 3000 万采样点、三个各 1000 万点的通道。以下为同一发布测试进程、同一数组上比较原扫描路径与索引路径；全部显示桶逐项一致。

| 通道 | 原扫描 | 精确索引 | 原扫描/索引 |
|---|---:|---:|---:|
| CH2 | 10.170 ms | 0.559 ms | 18.2 倍 |
| CH3 | 10.099 ms | 0.820 ms | 12.3 倍 |
| CH4 | 10.281 ms | 0.595 ms | 17.3 倍 |

发布构建另执行 200 次不同范围与分辨率的连续查询，覆盖 512/1024/1500/2048 桶：中位数 0.775 ms、P95 1.883 ms、最大值 2.518 ms，查询计算总计 176.142 ms。每隔 25 次重新与原扫描路径逐桶对照；输出上限保持 2048 桶，数组和索引仍为共享对象。

该样本索引数组为 **6 MiB**，约为原始 X/Y 双数组载荷的 **1.31%**。这不是进程总内存增量或峰值内存测量，不能把进程占用表述为“只有 6 MiB”。构建时还有临时分配和既有解析器内存。

发布测试的一次文件加载（含索引构建）为 547 ms；没有在同条件冷缓存下对旧版加载做 A/B，不宣称打开文件因此变快。调试路径本次加载约 2992 ms，此前一次为 2547 ms，二者也不能用作严格的加载性能对照。索引的收益主要是后续重复平移、缩放和叠加。

上述时间仅覆盖后台视口计算，不包括 IPC 序列化、WebView 绘制、鼠标输入和显示刷新；不能等同界面响应时间、帧率或整个程序的 CPU 降幅。
