# WiParse AI 契合度与 Token 利用效率评审

评审日期：2026-11-10。对象：`cursor/four-job-shell-and-marketplace` 当前工作树，包含尚未打包的测试报告 AI 侧栏。基准提交为 `d4362bc4ceb6eb028815a4281cf5b75df04d4fd0`，**不能用该提交号代替本次工作树内容**；相关文件哈希见验证目录。

## 1. 结论

**当前方案已经具备真实的平台操作能力，不再只是聊天框；但执行协议、上下文管理和业务工具之间仍有明显断层。Token 效率存在结构性浪费，尚不能依据现有统计证明“整体利用率很低”或给出可信的百分比。**

具体判断：

1. **大日志本地处理的方向正确。** 搜索、统计、事件提取、时序处理在本地执行，模型接收摘要；曲线数据可通过宿主缓存直接进入数据分析页面，不需要模型转述全部采样点。这部分具有实际节省 Token 的架构基础。
2. **简单任务和周期监控的固定开销偏大。** 串口手动 Agent 的固定提示词及函数定义组件合计约 **26.3 KiB/请求**，不含用户问题、证据、历史和动态状态。大量说明与当前任务无关，或与原生函数定义重复。
3. **多轮工作的效率损失主要来自重复上下文、协议返工和工具粒度，而非输出上限太小。** 再增加最大 Token 数或直接更换 Agent 框架，不能解决这些问题。
4. **发现一项优先于省 Token 的正确性问题：报告分页结果被再次截断。** 默认返回 80 行，Agent 通用压缩只保留前 16 行，但 `next_line` 仍为 81。若模型按游标继续，会跳过第 17–80 行。已用当前函数复现，不能把这种信息丢失称为优化。
5. **现有 usage 统计不足以做成本绩效判断。** 有服务返回的输入、输出、缓存统计，但缺少与任务成功率、修复轮数、重复证据、信息覆盖率关联的持久化账本；本次也没有调用真实付费模型采集业务样本。

建议顺序：**先修证据完整性和协议一致性，再拆分按任务加载的工具与上下文，最后用任务级数据验证节省幅度。**

## 2. 评审方法与证据边界

- 阅读实际上下文组装、原生工具协议、执行循环、日志处理、报告读取、跨工具数据通道与 usage 实现。
- 使用现有 Core 编译产物运行只读测量程序，计算实际目录与函数定义的序列化字节长度；串口的专用方法集合按源码中的相同规则重建。
- 提取当前 `bounded_evidence` 与 `clip` 函数，构建合成 80 行报告分页结果，验证经过压缩后送往模型的数据形态。
- 未读取个人 AI 配置、密钥或私有日志；未调用外部模型或仪器；未改动生产功能代码。

测量单位为 **UTF-8 字节**，不是 Token。函数定义组件的测量还不包含 HTTP 请求中的外层工具包装、消息包装、额外短指令等，不能当作完整请求长度。实际分词、缓存与计费要按具体模型和服务返回数据验证。

证据位置：`docs/verification/ai-fit-token-review-20261110/`，包含测量代码、输出、截断复现及工作树文件哈希。

## 3. 与 WiParse 各功能的契合程度

以下为代码与调用链评审结论，不是实测模型准确率或工业认证。

| 功能域 | 已形成的结合 | 主要不足 | 判断 |
|---|---|---|---|
| 串口日志分析 | 全范围本地扫描、字段发现、事件/时序提取、搜索与定位、队列、来源绑定 | 独立执行循环与全局 Agent 行为不同；提示词过长；统计到物理事件/根因仍依赖模型正确选择规则 | 较高，但复杂任务稳定性仍需提升 |
| 串口监控 | 本地规则即时告警；云端按新数据周期分析；无新增数据不请求；连续失败退避 | 有新数据即可能周期请求，尚未按风险/状态变化充分抑制健康重复窗口；云端不是保护联锁 | 本地监控较好，云端策略效率一般 |
| 波形/协议 | 使用实际采样测量、协议解码、时间区间和帧证据 | 界面动作、低层 API 和工程分析任务之间的语义封装不统一；不能把文本摘要等同视觉观察 | 中等 |
| 数据分析 | `log.analyze(retain_dataset:true) → data.present(query_id)` 本地数据直连；可检查统计结果 | 需要模型先正确选规则并保留数据；缺少稳定的一体化业务任务入口 | 数据路径契合度高，任务编排中等 |
| 测试报告 | 独立侧栏、原文分页、检索、工程内对比、生成独立分析报告 | 分页二次截断问题；图片像素不可见；对比维度/报告结构尚非统一类型 | 已接入，但完整报告分析暂不应视为可靠验收完成 |
| 仪器控制 | 实际设备发现、类型化命令、任务结果、权限和取消检查 | 通用目录参数多为示例，缺少完整模型可用 schema；发现/设定/测量/验证仍需多轮组合 | 接口层中等偏高，业务自动化中等 |
| 集成测试/插件 | 配置草案、预检、执行状态、宿主等待；不靠模型反复轮询 | 插件差异、测试前提、失败诊断和能力声明尚未统一成专业任务模型 | 中等 |
| 计算器 | 调用确定性计算引擎，区分计算与测量 | 非计算任务也携带计算器 schema；简单确定操作缺少轻量路径 | 执行契合度高，上下文选择不够精细 |
| 全局 Agent | 共享服务、证据 ID、宿主执行、统一能力发现；报告侧栏复用 Session | 串口仍另有执行循环；长期记忆、跨任务状态和上下文压缩未完全统一 | 平台基础已具备，尚非统一专业 Agent 内核 |

当前目录有 **48 个 canonical 工具条目、102 个已发布平台 API 方法**。两者有封装和重叠，不能相加为 150 种独立业务能力；也不能据此宣布所有 GUI 操作和真实设备场景均已验证。

### 专业性仍缺少什么

现有 profile 已包含充电中断、状态转换、证据/推测区分、测量质量和测试判定保护等工程要求，这是正确基础。但本次审查的 AI 主链主要通过提示词和通用工具组合表达专业知识，尚未形成可版本化的“产品/协议/测试阶段—前提—测量—规则—证据—结论”业务模型。

因此，接口数量增加后，模型仍可能不知道：某任务应该先读哪个状态、需要哪种测量、何时信息足够、何时必须询问工程条件。专业性提升应优先补这些关系，而不只是继续增加方法名。

### 4.3 周期监控

自动监控不发送原生函数定义、没有手动会话历史，也不附完整本地日志目录；但仍附带串口契约、平台文字目录和工作流/profile。相同静态组件口径下约 **14,338 字节/请求**，另加观测数据。

代码会跳过没有新增数据的窗口，这是已有优化。但健康日志持续增长时，仍可能持续请求。默认 5 秒、服务响应足够快且数据持续新增的理想条件下，理论上限约 720 次/小时；真实频率受延迟、单请求串行、失败退避等约束，不能把上限当成实际使用量。监控入口需要独立的轻量契约和事件变化触发策略。

## 5. 问题清单与优先级

### P0：通用截断破坏报告分页语义

证据：`test_report/ai_read.rs:22` 的分页读取与 `ai/agent.rs:181、612` 的通用压缩串联。

复现结果：

```json
{"original_page_rows":80,"visible_rows":16,"last_visible_line":16,"next_line":81,"truncated":true,"gap_if_following_next_line":64}
```

压缩有 `truncated:true`，并非完全隐藏截断；但原游标没有同步调整。模型即使按宿主提供的 `next_line` 正常操作，仍可能漏读 64 行。它也可能识别截断并主动从 17 行补读，但不能依赖这种推断保证正确性。`agent.evidence` 保存的是压缩后的数据，不能自动召回已丢掉的行。

同类风险还包括超过 16 项的报告索引/平台目录：原列表变成 `{items,truncated,...}`，类型发生变化，原分页偏移不变。默认小页未必触发，但较大合法页会触发。

**调整：** 由工具自身按预算分页，返回 `returned_range / next_cursor / has_more / coverage`，执行层不得再次裁切有游标的结果。通用兜底只用于未知形状，必须报告可恢复的截断位置。先修正确性，再讨论降低正文体积。

### P1：原生与 JSON 契约没有真正分离

`engineering_agent.rs:395` 的共享契约仍直接要求输出 JSON envelope；原生路径又声明使用函数调用与最终 Markdown。串口契约已经明确区分两种模式，但 Auto 模式仍携带大量 JSON 动作示例。

此外，新 `platform.invoke` 允许经权限校验调用现有平台接口，而旧契约仍笼统禁止某些发送/配置/路径操作。模型可能在“目录说能调用”和“契约说禁止”之间摇摆。宿主有拒绝与确认机制，不能由冲突文字代替它。

**调整：** 原生、JSON 兼容、自动监控分别构建契约；权限描述从同一能力定义生成。原生模式只发送原生协议，禁止和允许条件精确到动作及授权范围。错误修复应针对具体 schema，避免重新发送整套长篇教导。

### P1：能力发现是广覆盖，但参数理解仍偏弱

`wiparse_call` 使用方法枚举加通用 `params:object`；平台目录提供示例，尚非统一完整参数 schema。模型通常需要额外 help/catalog，再试参数，错误时继续修复。共享目录还无条件附加计算器完整字段说明，即使正在分析报告。

**调整：** 建立单一能力描述：参数 schema、单位、枚举、前置条件、输入输出类型、权限、异步完成条件。先加载当前任务相关能力；需要时检索其余能力。不要为了减少提示词而删除可发现性，也不要把所有接口全部塞进每次调用。

### P1：两套执行循环导致调用成本与行为不同

串口支持同轮最多四个独立只读调用；共享 Session（包括报告侧栏）要求恰好一个原生调用，多个调用会进入修复流程。传输层虽接受最多四个调用，上层规则不同。

**调整：** 统一执行内核与权限/批处理策略；保留不同页面的 UI、来源绑定和业务 profile。独立只读任务可合并，存在依赖或硬件状态变化的动作必须顺序执行。合并调用不能用来突破控制确认或混合来源。

### P1：上下文保留有预算，却缺少任务语义压缩

两条链保留最近六轮原生工具历史，序列化预算约 96 KiB；删除的是整轮，且至少保留一轮，因此单轮过大时该值不是绝对硬上限。Workflow 保留最多 48 项、总计 512 KiB 证据，单项超过 24 KiB 只保留摘要；证据索引的 entries 最多约 16 KiB，available_ids 另附。

这比无限堆历史好，但存在三类开销：

- 工具正文、索引、任务状态和此前任务证据可能重复出现。
- 六轮窗口滚动后，缺少的关键信息可能需要再次召回甚至重扫。
- 摘要字段对日志数值/事件/时序更友好，对报告章节、设备前提、插件配置差异的语义表达较弱。

若固定上下文为 B、每轮新增工具内容为 E，N 轮的输入处理量大致包含 `N×B + Σ min(i,6)×E`，还未计动态索引、输出和修复。缓存可以改变收费，并不使这些重复输入消失。

**调整：** 用结构化任务状态保留目标、已证事实、待解问题、来源修订、已执行动作与结果；正文留在本地证据库，通过精确 ID/范围按需召回。保留关键事实与未完成目标，不能只按轮数丢弃。工具调用 ID 和供应商要求的续接字段必须维持合法配对，不能随意删除 reasoning 字段来“省 Token”。

### P1：统计足以显示用量，不足以衡量利用效率

`ai/usage.rs` 能识别多种 input/output/cache 字段，不把缺失值当零，这是正确实现。但当前主要按任务/会话汇总，没有完整的持久化调用账本和业务成败关联。

流式请求也未见统一发送 `stream_options.include_usage`；某些服务需要该选项才给出流式用量，所以应按供应商能力协商，不能假设所有流式请求都有完整 usage。不能一刀切添加到所有兼容端点，否则也可能产生兼容问题。

**调整：** 记录 task/call/source revision、模型、工具、成功/失败/取消/结果未知、输入/输出/缓存/推理统计（服务提供时）、延迟、修复原因、证据覆盖与最终任务结果。缺失字段明确标记。默认只保存元数据与摘要哈希，不保存密钥或完整原始日志。

### P1：Token 预算仍主要是字节和轮次预算

当前输入总量按 1 MiB 等字节阈值控制，任务按 16/32 轮等次数控制，输出配置上限可到 262144。这些是边界保护，不是模型上下文窗口或业务成本预算。

提高 `max_output_tokens` 不等于每次必然消耗这么多，但也不代表端点接受该值。当前不能据此判断输入是否挤占输出空间、一次修复是否超出成本收益。

**调整：** 引入可核实的模型能力配置和保守预算估算，区分输入、输出、工具结果、修复及监控预算；以服务实际 usage 校准，不用统一“字符除以四”冒充精确计数。

### P2：监控请求应按信息变化分级

已有无新增数据跳过、错误退避、本地告警独立运行；但还缺少更细的状态变化、新异常、严重级别、重复模式合并、冷却与迟滞策略。

**调整：** 本地规则/统计触发即时告警，云端负责解释和复杂关联；保留低频健康摘要，异常/阶段转换触发额外分析。不能把降低云端频率误作降低本地捕获与保护要求。

### P2：领域任务缺少稳定的业务封装

“找到充电中断原因”通常需要格式识别、实体/时间范围、状态转换、前后因果候选、相关波形/协议、最终说明。现在主要靠模型多次组合通用接口。

**调整：** 增加由宿主执行的可验证工作流，例如报告对比、充电周期取证、协议质量检查。输入为业务目标和显式工程条件，输出为事实、规则版本、覆盖范围与证据。模型解释未知语义，确定性步骤由本地执行。不得用固定关键词把所有产品日志硬套成同一种断充规则。

## 6. 不能为了“省 Token”削弱的已有能力

- 本地日志搜索/聚合、事件提取与显式覆盖信息。
- 实际采样点直接进入数据分析工具，最多 250,000 条本地提取记录，而非由模型重建点数组。
- 实际设备 job 的宿主等待和状态核验；避免模型轮询。
- 只读任务不反复要求用户确认；设备动作仍确认具体参数。
- 来源绑定、取消、结果未知不重放、历史证据不冒充实时测量。
- 标记截断、缺失和不可见图片像素；不能用省略风险信息换取更短回复。

Mermaid 本地渲染不会额外调用模型；模型生成图表源码仍消耗输出 Token。流式显示主要改善感知响应时间，**本身不构成减少 Token 的证明**。

## 7. 如何判断 Token 利用率

不要用单一的“输出/输入比”或“上下文窗口占用率”评价效率。长输入可能是必要证据，短回答也可能是高价值结果；缓存命中高也不代表业务正确。

| 指标 | 定义/用途 |
|---|---|
| 每个成功任务的输入/输出 Token | 分开报告，并附失败任务的消耗，避免成功样本偏差 |
| 每个成功任务成本 | 按实际服务价格、缓存类别和 usage 计算；无价格或 usage 不报金额 |
| 一次完成率 | 不需要用户重复催促或同意只读操作的任务比例 |
| 协议修复开销 | 因 envelope、schema、无效调用导致的额外请求和 Token |
| 重复证据率 | 同一来源修订、同一范围/结果重复发送的字节/分词占比 |
| 信息覆盖完整性 | 实际送到模型的范围与工具声称范围是否一致，分页是否有缺口 |
| 缓存命中及统计完整率 | 缓存只按服务报告认定；usage 缺失需单列 |
| 延迟 | 首字、首个有用证据、最终完成的 p50/p95 |
| 操作质量 | 执行成功率、误操作、重复输出改变、无法确认结果次数 |

本次没有真实任务的完整账本，**不提供“利用率只有某百分比”或“必省某百分比”的结论**。80→16 的复现是行覆盖问题，绝不是 Token 利用率 20%。

## 8. 改进顺序和验收要求

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| A：正确性 | 语义分页、截断恢复、原生/JSON/监控契约分离、按实际权限描述能力 | 80/200 行分页不漏行；索引无跳项；原生请求不再要求输出 JSON envelope；非法动作仍被拒绝 |
| B：可观测性 | 持久化任务调用账本、usage 完整性与修复原因 | 可以解释每次请求为什么发生、实际花费是否已知、任务是否成功；不泄露密钥/原始日志 |
| C：上下文与工具 | 单一 schema 注册表、按任务加载、结构化状态、证据缓存与差量摘要 | 轻任务固定组件显著低于当前基线；真实证据召回完整；源变化/取消/权限行为不回退 |
| D：专业工作流 | 报告对比、充电周期、协议质量和仪器测试工作流 | 同一事实结果可复验；不虚构根因、曲线、PASS；复杂任务轮次与修复减少 |
| E：监控策略 | 事件驱动分析、异常合并、健康低频摘要 | 同一数据回放下告警召回和时效不下降，健康重复窗口请求减少 |

暂不建议因本次问题直接替换整套 Agent 框架。缺陷主要发生在 WiParse 自己的契约、分页、业务接口和上下文层；换框架仍需处理这些问题，还可能引入额外消息格式和运行依赖。

### 建议回放基准

建立不少于 30 个固定场景，覆盖：短日志搜索/跳转、大日志事件统计、多格式充电周期、波形测量与协议质量、报告分页/对比/异常证据、仪器模拟任务、插件预检、控制拒绝/取消、来源变化、格式错误恢复。每个场景保留预期证据范围与可验证结果。

先用本地模拟服务验证协议、权限和证据不丢失，再在用户认可的模型/成本预算下采集真实 usage。比较时固定模型与参数、相同数据和任务，冷热缓存分开，重复执行并记录失败样本。优化是否通过以质量不回退为前提，不以回答变短或丢证据来制造节省。
