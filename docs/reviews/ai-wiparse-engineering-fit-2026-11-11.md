# WiParse AI 工程契合度评审与改进方案

日期为 2026-11-11。对象为 egui 分支 `cursor/four-job-shell-and-marketplace` 的当前工作树。提交基线为 `d4362bc`，含未提交实现。对应 1.2.2 DataLayout 预览版主程序 SHA-256 为 `21a716ed3f285c7506b523722ffba7a4766afc6ea55426871d0b34db99d05750`。

## 一、决策摘要

WiParse AI 与工程数据处理的契合度高，与跨页面任务交付的契合度中等，真实模型和设备组合下的诊断可靠性仍待测量。最成熟的路径是「指定日志 → 本地提取 → 携带来源的点列 → 展示或生成带曲线的报告」。最容易使用户失去信任的路径是「模型给出一个看似完整的解释 → 页面显示分析完成 → 实际缺少必要输入或交付物」。

当前应保留 Rust 宿主的本地计算、证据缓存、设备授权和异步作业机制。开发顺序建议先统一完成状态和证据要求，再打通数据集与工程任务，最后按任务成功率评估工具路由和模型成本。没有证据表明现在替换整个 Agent 框架能修复下述问题。

## 二、逐域评估

判断维度为入口可达、宿主是否真实执行、结论能否追溯、同一任务能否交付到目标页面。表中的判断针对已审阅路径；代码覆盖、业务成功率和真机精度须分开统计。

| 功能 | 已形成的工程能力 | 仍影响使用的边界 |
|---|---|---|
| 串口与日志 | 当前范围可自动取证、搜索跳转、字段发现、事件与时序提取。模拟交互已覆盖一次提问、修复停滞、读证据和完成。 | 专用串口循环与共享助手的完成条件不同。关键词命中、物理事件、推断原因是三个不同口径，仍需现场真值校准。 |
| 在线监控 | 本地规则与云端分析分层，无新增数据可跳过请求。 | 健康日志持续增加时仍可能重复分析；实际告警召回、最坏延迟和每设备小时成本缺少联合基准。 |
| 数据分析 | 同一选择器可处理键值、分隔列和嵌套 JSON。当前文件可在本地扫描；串口时序点列可经宿主呈现。 | 文件统计与串口点列具有不同返回契约。无时间戳的文件也可能需要按样本序号绘图，目前这条跨工具链不完整。 |
| 波形与协议 | 通道、时间测量、解码、帧读取均有宿主入口，可依据真实采样取证。 | 跨日志和仪表的时间对齐、采样精度、探头与阈值是诊断前提。仅有各自的测量结果不足以认定异常之间有因果关系。 |
| 测试报告 | 支持索引、正文分页、跨报告检索、证据召回，生成的 Markdown 可附真实曲线和 CSV。 | 报告读取工具不解析图片像素。只有截图时，波形频率或死区应标为缺少原始测量；正文引用证据 ID 也不能独立证明其中每项推论。 |
| 仪器控制 | 具备设备发现、类型化操作、作业等待与结果回收。 | 指令完成、设定值回读、独立仪器实测应作为三个状态。工程验收还需覆盖断线重连、设备替换和超时后的实际状态。 |
| 集成测试与插件 | 宿主能预检、启动并等待实际运行，区分进程退出与产品判定。 | 不同插件的资源前提、产物、判定来源和可恢复动作需有一致描述，否则模型只能逐插件理解返回值。 |
| 计算器与通用平台 API | 确定性计算可复用既有实现；能力目录可发现方法和作用范围。当前源码列出 49 个规范 Agent 工具条目。 | 低层平台不少方法以参数示例描述。工具数量无法说明某个工程流程的必需输入、允许范围和成功后置条件。 |

## 三、关键缺陷与修正设计

| 优先级 | 当前证据与后果 | 建议修正及验收 |
|---|---|---|
| P0 · 完成状态失真 | 共享 Session 接收原生 `wiparse_answer` 时允许 `completed` 和 `needs_input`，解析时只留下 reply。当无开放目标、无已登记阻塞时，两者均可走到“分析完成”。已登记开放目标时，真实缺参也可能触发继续请求模型。见 `ai/agent.rs` 原生响应解析和结束分支。 | 端到端保留结构化终态。以合成响应分别回放无计划缺参、有计划缺参、取消、部分完成和已交付；核对 UI、审计记录和是否继续请求模型。普通能力问答允许直接完成。 |
| P1 · 数据提取与呈现脱节 | `data.extract` 返回 matched、missing_or_invalid、min/max/mean，没有 query_id 或点列；`data.present` 从串口面板按 query_id 取数据。用户在数据页要求“提取这两列并画图”时，宿主不能直接把前者结果传给后者。 | 抽取共享本地数据集句柄，文件和串口均可生产；声明横轴类型、字段、单位、来源版本、有效区间及缺值。先覆盖 CSV 无时间列、JSONL 带时间列和串口时序三类；逐点比对图、导出和源记录。 |
| P1 · 扫描完成容易被理解为成功识别 | `agent_extract` 按 header 匹配记录；没有匹配仍返回 `ok:true, complete:true, records_scanned:0`。现有 CSV 回归也显示表头与空数据单元一起进入 missing_or_invalid。全量遍历、记录发现率、字段有效率在工程上含义不同。 | 分别返回扫描覆盖、记录数、表头策略、空值/非法数和识别状态。明确选为表头时才排除，由样本预览验证。零帧或全空值时返回具体原因及下一步选择，不得输出“没有异常”。 |
| P1 · 多目标任务缺少统一交付检查 | 串口有原生答案引用和任务回放；共享循环接受部分普通文本作为最终答复。开放目标检查依赖目标已经登记。请求“时长、曲线、协议核查、报告”时，是否每项都有对应产物缺乏统一保证。 | 对这类请求建立可检查的交付清单，逐项绑定区间、统计结果、图形句柄、帧范围和报告 ID。允许输出可用部分，缺什么就显示什么；不得要求用户反复回复“继续”。 |
| P1 · 跨仪器诊断缺少测量条件 | 波形、日志、报告和仪器分别提供证据入口；宿主证据可记录来源及单位。但本次未发现覆盖这四类来源的统一时钟对齐和误差传播流程。 | 增加时钟域、对齐事件、偏差范围、采样率与质量字段。只有时间区间可比时才关联事件。用已知时差、丢包、低采样率三类用例检验误关联。 |
| P2 · 参数发现和用量评价粒度不足 | 平台目录可分页，示例不代表默认值；调用 usage 已有任务标识、请求结果及提供方用量。请求成功不等于交付成功。 | 从实际校验生成高频工具参数说明、枚举、单位与完成条件；串联任务结果、协议修复次数、用户确认次数、首证据延迟和提供方 Token。缺失 usage 单列。 |

以上 P0/P1 为本次源码评审结论，尚未在本次修改生产代码。状态丢失和统计返回形状可直接从实现确定；跨仪器诊断属于能力缺口，未把它写成已观测的现场误判。

## 四、用一个真实需求串起改进

以“分析 20:05:09.865 开始的一轮充电，计算时长，画功率曲线，检查协议通信并形成报告”为验收主线：

1. 锁定当前来源与版本，定位指定时刻的充电状态转换。重复时刻优先用上下文消歧；只有存在多个无法区分的轮次时才询问用户。
2. 在本地识别起止事件，返回时间、行号和判据。若日志在充电中结束，只给已观察时长及右端缺失说明。
3. 对齐电压和电流、明确单位，再计算功率。不同采样时刻须声明允许的配对误差；缺失值保留空档。用本地点列生成图和 CSV。
4. 对同一区间检查协议帧、错误和可观察范围。若只有串口文本而没有通信帧或可解码波形，列出可确认的日志现象，将协议层结论标为证据不足。
5. 生成可重开的报告，逐项链接日志行、帧、图表和计算口径。报告可在证据不全时交付，结论显示覆盖范围；界面只有在交付状态明确后才结束任务。

## 五、分批落地与放行条件

| 批次 | 实施位置及影响 | 放行条件 |
|---|---|---|
| A · 先修可信度 | 共享 Session、串口适配器、报告状态栏。复用已有读取与设备权限，不改变设备指令。 | 缺参、取消、部分结果、已交付在两入口表现一致；已授权只读流程无额外确认；真实缺参仅问必要问题。 |
| B · 贯通本地数据 | 数据分析、串口数据缓存、绘图和报告产物。先兼容现有 query_id，再添加文件数据集生产端。 | 同源点数、单位、缺口、统计与导出一致；切换文件、取消、缓存过期返回明确状态；大文件内存和界面交互与当前基准对比。 |
| C · 专业诊断 | 先交付充电周期与断充两条任务，再扩展协议质量、PWM 频率/死区和插件失败诊断。 | 每条任务有已知真值、证据不足和反例；验证错误归因、漏检和误报；仪器动作以受控测试台的实际回读验收。 |
| D · 成本与响应 | 接入任务级指标；按任务提供所需工具，保留按需能力发现。周期监控变更先以离线回放比较。 | 在相同模型版本、固定数据和等价任务质量下，对比每个成功任务 Token、P50/P95 响应及告警延迟；质量退化时保留原策略。 |

建议建立匿名、版本化的回放集，同时覆盖串口与共享入口、原生与 JSON 协议、至少两种实际使用的模型端点。按简单问答、单源提取、多源诊断、设备控制分层公布分母。收费实测应记录提供方实际 usage；字节数、缓存命中 Token 和请求次数分别呈现。不能直接把旧版固定提示字节降幅换算为新版费用节省。

## 六、复核依据与限制

- 本次重新运行当前 GUI 测试产物的四组定向回归，串口任务工作流 6 项，共享 Agent 整改用例 6 项，无时间列文件统计 1 项，含真实点列的便携报告 1 项，合计 **14 项通过**。测试包括合成输入和模拟模型响应。它们能验证宿主流程，不能测出真实模型选择工具和归因的准确率。
- 对照上一次整改，报告连续分页、长行续读、区分原生与 JSON 协议、按任务记录 usage 已有实现和回归记录。本报告未将已修问题重新列为当前缺陷。前版测试的固定组件测量不作为本次预览的实测 Token。
- 本次未调用付费模型、未操作真实仪器、未读取用户日志，未得出模型间优劣、现场告警召回率或实际费用降幅。建议先交付 A、B 两批，再用 C、D 的业务数据决定模型或框架选型。
