# WiParse 工程 Agent 系统架构对标评审

评审基线为 egui 主线 1.2.4，提交 fcbd67e。评审覆盖从串口和共享助手发起请求，到宿主调度、设备回执、证据、报告恢复和最终交付的路径。Codex 一侧采用公开的 App Server 协议与官方工程案例。两者适用领域不同，本评审评价可观察的架构行为；模型正确率、现场响应时间和真实 Token 成本需另做同条件对测。

## Codex 的哪些设计值得移植

Codex App Server 将持久会话、一次任务交互和工具执行项分别建模为 thread、turn、item。客户端订阅生命周期事件，并通过带身份的请求响应审批。一个命令被批准、开始执行以及最终结束有各自的消息。这样 GUI 可以从宿主状态还原执行过程。官方长任务案例还将目标、验收条件、当前进展和已知限制保存在项目中，下一轮可根据真实产物继续工作。[Codex App Server 协议](https://developers.openai.com/codex/app-server) · [OpenAI 长任务案例](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)

WiParse 可以直接借用执行身份、生命周期和可验证交付这三个设计。硬件操作还多一层约束。例如示波器驱动返回 Stop 成功，只足以证明驱动处理了命令。要证明故障前后窗口确实被采到，还要读回采集状态、样本范围、触发时刻与数据质量。

## 分层评审与整改

| 层级 | 当前实现 | 发现及影响 | 优先级和处理 |
|---|---|---|---|
| 任务与执行身份 | 共享 Session 和串口 Run 各自处理模型轮次，两者共用核心 Workflow。新任务切换时保留证据便于追问。 | 旧报告可读的同时也可被计划引用为本轮新报告。重复测试同一产品时，用户可能看到上一轮结果被算成本次交付。 | 高。本轮给证据绑定任务代次。产物或操作步骤要有本轮证据支持，历史解释和显式恢复仍可使用旧资料。 |
| 计划与宿主验收 | 更新计划时核对未决步骤 ID，模型可以提交新标题和类型。 | 模型用同一 ID 将已声明的报告文件步骤改为一般分析，并以失败读回结束该步骤。若用户原句被宿主识别为生成报告，独立目标仍待办；对于仅由模型登记的步骤则缺少这层保护。 | 高。本轮锁定已明确的交付类型。允许初始一般分析细化为具体产物，可通过新步骤登记新增工作。 |
| 协议证据 | 整体协议核查和定位具体帧原本共用同一完成条件。 | 配置了过滤条件后，即使返回空页，全局帧数仍可大于零。对于“标出对应帧”，缺少具体可引用的帧号与时间。 | 高。本轮独立登记帧定位，要求返回有效帧号和有序起止时间。跨设备对应关系仍需同步证据。 |
| 执行与授权 | 两个入口共用部分工具和工作流，但各自维护轮询、超时、取消、重试和历史。设备回执已有 job_session 和 job_id。 | 新增一种设备或提供方时要维护两套状态迁移。共享入口的未决写操作集合会随新任务清空，恢复链能提示人工读回，但新任务仍可能只出现常规操作确认。 | 高。将设备未决结果绑定工位、设备身份和操作，从设备服务查询。先让两个入口消费同一串模拟回执，再迁移授权和取消路径。见 [共享入口](../../crates/wiparse-gui/src/ai/agent.rs)、[串口入口](../../crates/wiparse-gui/src/serial_tool/ai_chat/platform.rs)。 |
| 大文件与证据回读 | 文件提取、波形和曲线已有本地处理及来源摘要。报告页读取支持行号和行内偏移。 | 每次报告分页都从文件开头重扫，读取器只允许从文件头累计读约 16 MiB。大 CSV 后段无法靠连续翻页到达；搜索可命中关键词，却不足以证明附件已被完整审查。 | 高。改用绑定文件身份的绝对字节游标与行号。验收采用 32 MiB 文件、跨边界 UTF-8、超长单行，以及换文件后的游标失效。见 [报告读取器](../../crates/wiparse-gui/src/test_report/ai_read.rs)。 |
| 重启与工件 | SQLite 保存任务、步骤和引用；报告可重新校验摘要；普通内存证据需要重取。 | 长任务查到一半重启，已完成的昂贵提取可能重算。数据源被替换、设备重启与普通应用退出需要不同恢复策略。 | 中。按来源摘要、规则版本、时间窗和单位保存可重算结果索引。先实现只读分析恢复，设备命令继续依赖现场读回。见 [任务记录](../../crates/wiparse-gui/src/ai/journal.rs)。 |
| 成本与智能评测 | 已有冻结输入、匿名评审和费用汇总工具。 | 基准运行器仅在成功交付路径读取 answer 中的 total_tokens。超时和失败消耗的 Token 可能缺测，同组比较不能直接推出节省比例。 | 中。按请求 ID 旁路记账，把失败和重试成本计入分子，单列用量缺测率。见 [基准运行器](../../scripts/run-engineering-benchmark.py)。 |

本轮实现位于共享核心，由两个入口直接复用。工具的原生计划 schema 与宿主验证器共用交付类型清单，减少新增类型只在部分提供方生效的风险。[核心工作流](../../crates/wiparse-core/src/ai/workflow.rs) · [原生工具定义](../../crates/wiparse-core/src/ai/tools.rs)

## 建议的运行架构和迁移次序

1. **将任务状态迁移集中在宿主。** GUI 发出“开始、补充、取消、确认”，由单个运行时给出任务、执行项和结果。串口和报告页消费相同事件。先迁移只读调用，以相同输入回放两个入口，要求终态、证据、产物、取消边界一致，再移动设备写操作。
2. **按实际回执推进硬件状态。** 一次执行关联设备会话、命令身份和采集批次。明确区分已派发、驱动已接受、驱动已结束、仪器已读回、已取得样本和结果未知。未知状态写入持久记录。验收时模拟 USB 拔插、恢复后新建任务、迟到回执；未知刺激的自动重发次数必须为零。
3. **将领域结论绑定到工件。** “找出断充原因并标出对应帧”至少需要日志事件、时间窗、候选帧及两种时钟间的映射误差。若时间窗覆盖多个候选帧，返回候选范围和区分条件。现阶段新增的帧引用判据仅确认有可定位的帧，无法独立证明它对应指定的断充事件。
4. **冻结对照任务后衡量收益。** 让现版、候选版、通过同一组只读工具工作的 Codex 和人工参考流程分析相同输入。分别记录原始证据定位正确率、端到端正确交付率、误归因、未知设备操作、人工介入次数和每次正确交付的总 Token。对无波形、无时钟映射、无边沿的样本，正确指出缺测也应计为正确。实机保护和控制权须由工位单独验收。

下一阶段应优先修复报告读取边界和跨任务设备未决状态。这两项直接关系到“已完整审查”与“可以再次执行”能否被现场工程师信任。

## 验证记录

以 1.2.4 提交 fcbd67e 中的工作流为对照，向旧实现和修改后的实现输入相同的合成工具回执。结果如下。

| 场景 | 1.2.4 基线 | 修改后的共享核心 |
|---|---|---|
| 新任务引用上一任务的报告回执 | 接受，生成报告目标消失 | 拒绝，生成报告仍待办；历史证据可查 |
| 同一步骤从报告文件改为一般分析，并引用失败回执 | 接受改写；从用户原句独立提取的报告目标仍待办 | 拒绝改写，原步骤仍待办 |
| 要求标出对应帧，查询返回空页，全局帧数大于零 | 定位目标消失 | 保留定位目标；带帧号和有效起止时间的回执可完成该目标 |

Windows 上运行 wiparse-core 与 wiparse-gui 两个包的离线回归，共 640 项通过，8 项按现有测试标记忽略，0 项失败。以上结果验证宿主的状态判定。真实提供方的任务完成率、每次正确交付的 Token 消耗、跨仪器同步误差及设备断线恢复仍需独立测量。

## 2026-11-12 顺序实施记录

上文分层评审表描述 1.2.4 基线。本次在同一分支继续完成以下开发。

1. **断线恢复。** AI 提交仪器控制命令时，设备服务在入队前将操作登记到数据根目录下的 `agent-device-operations.sqlite3`。同数据根目录下的工程共用记录。操作键由厂商、型号、序列号和规范化命令生成，缺少序列号时使用资源地址。另存工作会话和作业号，驱动成功回执只能解除原作业的记录。运行中重复调用会返回进行中。断线、驱动报错或应用重启后，重复操作会显示设备和参数，操作员读回状态并确认后可以重新提交。确认窗口自身不会发送命令。串口和测试等其他控制操作会在当前工程的历史记录中检查相同操作的未决回执。此前版本没有保存物理身份的历史命令，仍可通过原任务记录核对。
2. **大报告分页。** `report.read` 返回 `next_cursor`，下一次传入相同报告、附件和 `cursor` 即可直接定位。签名包含文件身份、大小、修改时间、绝对字节位置、行号和行内偏移。替换文件、修改游标或重启应用后应重新开始读取。工具保留按行号读取的入口。超长行按原始字节位置分片，UTF-8 字符与 CRLF 可跨读取缓冲区，只有读到文件末尾才返回 `reached_eof=true`。单页仍有大小上限，避免把大附件一次性传给模型。
3. **统一执行。** 通用助手、报告助手和串口的跨工具调度共用 `HostItem` 处理即时回复、异步回复、内部状态轮询和终态。只有宿主登记的状态查询可以继续轮询。缺少后续状态查询的未决回执会结束等待并保留结果未知，避免重新派发原写操作。桌面串口助手的仪器查询、命令和截图也进入通用宿主。专属串口收发、日志选择和周期监控保留原适配层。两个手动助手共用模型协议修复预算，格式错误时只重试模型轮次。通用助手也支持任务内退回 JSON 协议。

跨时钟分析工具 `agent.align` 仅采用当前任务的日志与波形证据。有校准误差界限时返回所读帧页中与映射时间窗相交的全部有效帧号，缺少误差界限时返回空值；已检查但没有匹配帧时返回空数组。多个候选、分页范围和校准假设均影响现场解释。对象存储、长期成本记账和真实仪器对比评测属于后续路线。

**本次验收。** Windows 离线运行核心与 GUI 两个包，核心 326 项通过、2 项忽略，GUI 321 项通过、6 项忽略，合计 647 项通过、0 项失败。模拟仪器在设备 ID 变化后仍阻止重复单次触发，迟到的旧回执无法解除新操作。大于 32 MiB 的 CSV 从第一页顺序读到最后一页，共核对 16,384 个连续行号和对应行内容；另测超长 Unicode 行、替换文件及无效游标。即时与异步工具都通过了相同的回执序列，模拟提供方覆盖原生工具和 JSON 回复。真实 USB 拔插、物理输出及在线模型成本未在本次测试中测量。
