# WiParse GUI 迁移进展检查报告

日期：2026-11-08。检查对象：当前工作区的 Tauri / React 新界面、兼容宿主、核心会话层及 Testing Hub 配套代码。

## 1. 结论

当前工程已经从早期页面原型推进到**具有实际业务操作的迁移开发版**。Cursor 接手后的工作区在波形协议与测量、数据分析实时路径、报告目录与附件操作、计算器交互、公共工作台和隐藏宿主启动方面有实质增量；不能再沿用此前“协议分析与实时分析均未迁移”的判断。

但目前**尚未完成旧版功能等价迁移，也不具备替换现场稳定版的证据**。串口 AI、串口跟随滚动、仪器完整面板、工程配置往返和报告完整工作流仍有缺口；宿主退出、接口身份、性能与实际桌面验收也未闭环。五轮正式验收没有完成记录。

建议继续沿用当前“新界面 + 兼容宿主 + 复用核心”的路线。独立设备服务不是本轮必须先完成的重构；需要优先解决的是当前路线本身的兼容、退出、身份和功能等价问题。

本报告不提供总完成百分比。命令数量、页面数量及单测数量不能换算成功能交付比例。

## 5. 需要处理的问题

以下严重性针对迁移版本替换现场版的门禁，不表示本轮已发生硬件事故。

### P0-01：正常退出直接强制结束兼容宿主，未完成业务收尾

位置：`apps/wiparse-next/src-tauri/src/main.rs:841` 的 `stop_owned_host` 与退出回调；`crates/wiparse-gui/src/main.rs:125` 的父进程监视线程。

Next 退出时直接 `child.kill()` / `wait()`；宿主检测父进程结束后直接 `std::process::exit(0)`。这两条路径都没有先确认测试停止、串口尾行落盘、配置提交、设备任务结果和资源收尾。即使旧宿主已有正常关闭保护，这里也可能绕开它；父进程监视器还会在 `OpenProcess` 失败时直接走退出。

这是源码可确认的退出机制问题。数据损失或设备仍输出是风险推断，本轮没有实机复现，不能写成已发生事故。

建议：增加受控关闭请求与关闭状态；运行中明确选择停止并等待或保留宿主；完成记录刷新、任务账本保存和释放后才退出。强杀仅作为显式的故障处置，并保留结果未知及下次恢复信息。父进程不可访问与父进程已退出需要分开处理。

### P0-02：非 AI 控制路径仍无统一身份验证

位置：`crates/wiparse-gui/src/backend/mod.rs:380`；Tauri `invoke_legacy_at`。

目前仅 `ui.ai.*` 检查 Bearer。串口、仪器、工程写入、测试执行等仍经原本机接口分发。前端白名单、CSP 和 localStorage 恢复标记不能保护直接访问兼容宿主的调用者。

建议：在兼容宿主现有分发层统一校验会话身份，并同步适配 GUI、CLI、MCP 与 Node 客户端；保留可审计的兼容策略，不能只改 Next 后使旧客户端全部失效。无需为此先重写整套独立服务。

### P1-01：宿主就绪判定不核对产品、版本、能力或实例

位置：Tauri `main.rs:836` 的 `host_ready`、`host_executable` 与 `ensure_owned_host`。

`/v1/health` 返回成功便视为可接入，不解析协议或实例身份。宿主查找还允许同目录 `WiParse.exe` 及向上查找开发构建。旧版本、错误进程或端口冲突可能被误认为正确宿主。当前代码有按功能读取 `safe_*_version` 的局部能力判断，但不能代替统一握手。

建议：校验产品 ID、桥协议版本、必需能力、实例 ID、数据根目录及启动来源；捆绑宿主优先使用明确名称和清单。发现不兼容时给出针对性提示，不自动改连或重复提交命令。20 秒启动等待也应按单调时钟限定实际总时长，而不是仅按重试次数命名。

### P1-02：报告正文链接全部失去点击能力，附件展示仍偏目录化

位置：`apps/wiparse-next/src/ReportWorkspace.tsx:64`。

Markdown 的 `a` 组件直接返回 `<span>`，没有保留链接目标或点击处理，因此正文里的波形、文本证据和页内目录链接均无法按链接访问。与此同时，展开一次运行后又枚举除主报告外的全部附件。这与用户要求的“以 Markdown 为主体，证据通过报告链接访问，截图直接显示”仍不一致。

图片 `ReportImage` 和受限 `report_image` 链路已经存在，不能再判断为完全没有内嵌图片能力。但普通链接不能替代图片；被 `skipHtml` 跳过的 HTML 内容也不能保证呈现。

建议：按当前报告目录和工程边界解析链接；本地波形进入波形页、文本留在报告页、图片内嵌，锚点在页内定位；外部链接只在用户点击后处理。附件列表收为可选辅助区，隐藏索引和中间文件。分别验证 Markdown 图片、中文/空格路径、相对路径、缺失文件、越界和过期会话。

### P1-03：串口 AI 尚未迁移用户真正需要的功能

位置：`apps/wiparse-next/src/AiAssistant.tsx`。

组件明确为单次手动输入，不携带日志和历史，不提供自动监控或工具执行；回复使用 `<pre>` 而非现有 Markdown 对话呈现。该实现可用于简单询问，但不能替代用户要求的串口监控、数据分析、预警及授权设备操作。

建议：优先复用旧版已经实现的会话、采样、告警与受控工具接口，补齐上下文预览和控制授权状态；统一对话字体与 Markdown 样式。云端分析、确定性本地告警和设备控制应继续各自具有明确执行状态，不能让 AI 文本充当执行凭据或测试结论。

### P1-04：串口滚轮暂停跟随的原交互未迁入

位置：`App.tsx:407–436` 的日志轮询及 `SerialLog` 渲染。

当前每两秒重取尾部最多 500 行；`offset` 只由分页、搜索及“最新”等显式操作改变。日志容器没有相应的向上滚轮冻结状态。用户向上查看尾页时，数据仍可能被下一轮尾页替换；“最新”按钮也不等同于用户指定的底部向下三角恢复行为。

建议：保持现有最大行数参数，将接收与显示跟随分离；上滚固定当前视图及绝对行身份，下滚浏览上下文，用户触发底部恢复后再追随。覆盖满缓冲区、持续输入、已移出行、页切换及查找时的稳定性。

### P1-05：仪器控制仍是子集，电源通道布局与既有要求冲突

位置：`SourceControl.tsx:7–13` 与 `App.tsx` 的 `InstrumentWorkspace`。

电源仍通过一个通道下拉框共用参数表单，不是所有通道平铺。示波器现有入口主要是采集动作、截图和源文件，未形成旧版完整四通道、时基和触发控制面板。仅缩小卡片宽度不能完成既有面板的等价迁移。

建议：按实际能力生成通道卡片，保留用户要求的平铺关系；每通道独立编辑与提交状态，跨通道共享设备级互锁。小窗口可滚动，不能通过隐藏通道或切换选择替代已确认的布局需求。

### P1-06：性能、实时积压与恢复缺少对照证据

实时数据分析每轮最多读 2,000 行，处理完后再等一秒；持续高输入时存在积压风险，长期处理能力低于单纯按 2,000 行/秒估算的理论值。该判断来自调度方式，不是实测吞吐结论。当前还会按保留窗口重算显示数据，需要测量高负载成本。

建议：给出待处理量、已丢弃行数、采集与展示延迟；采用有界批处理和时间预算追赶。使用同一真实日志与波形比较旧版和 Next 的 p50/p95 延迟、CPU、工作集、采集丢失及连续运行。没有数据前不新增架构层或声称更快。

### P1-07：验证基线与发布组合尚未冻结

根 Cargo workspace 不包含 Next，根测试通过不能覆盖 Tauri。Next、兼容宿主、CLI/MCP、插件和运行时又必须匹配，当前大量文件未跟踪，提交号不足以复现组合。现有历史包不能作为本轮新界面的交付物。

建议：分别建立 Next 前端、Tauri、宿主/核心、插件及离线包验证入口，记录源码与组件哈希、桥协议、插件版本和数据兼容版本。五轮验收以冻结组合为对象。

### P2：代码组织与进度文档仍需整理

`App.tsx`、Tauri `main.rs` 继续膨胀，应按工作区和命令域拆分，在接口保持不变的前提下逐段迁移。不能用大量单行 JSX 或命令注册掩盖复杂度。

当前交接文档仍写“94 个命令”“18 项前端测试”，并同时保留“有自动测试的只有公共侧栏”等过时表述。历史架构评审又把尚未接入的协议与实时分析写作缺口。建议保留历史报告并标注其基线，以本报告和当前状态清单为新的事实依据，避免把旧评审当作当前进度。

### P1-08：插件标准测试入口依赖启动目录；版本断言也已过期

`npm test --prefix test-tools` 从包目录执行，而新增无线测试直接以 `recipes/wireless-whitebox`、`test-tools/runner.mjs` 等相对路径定位仓库文件。仓库中的实际模板在根目录 `recipes/`，并不位于 `test-tools/recipes/`。因此该标准入口本轮得到 336 通过、12 失败，其中 11 项为模板定位失败，不应据此断言无线业务逻辑有 11 项错误，也不能忽略测试入口本身的问题。

另一失败发生在 `test-tools/lib/plugin-contract.test.mjs:80`：测试固定要求示波器串口插件版本 `0.6.2`，实际清单已为 `0.7.1`。这属于测试与插件版本脱节，不能解释为清单 Schema 校验失败。

本轮另从仓库根目录执行同一完整测试集合，结果为 **347 通过、1 失败**：11 项模板定位失败不再出现，剩余为上述版本断言。这确认了两类问题应分开处理。建议所有 fixture 和 runner 路径以测试模块位置解析，统一支持仓库根目录与 npm 包入口；版本检查应根据实际发布契约维护，不要为了凑绿直接放宽全部检查。

## 7. 建议推进顺序与验收条件

| 顺序 | 任务 | 通过条件 |
|---|---|---|
| 1 | 固定当前组合与更新差异清单 | Next/宿主/核心/插件/CLI/MCP 可按清单复现；逐项标明已实现、已自动验证、已桌面验证和已实机验证 |
| 2 | 宿主身份、启动和退出 | 错误服务/旧版本明确拒绝；运行中退出不丢尾行、不绕过关闭保护；未知设备状态可恢复；只管理自己启动的宿主 |
| 3 | 控制接口身份一致性 | Next、旧 GUI、CLI、MCP、插件保持兼容，未授权请求被拒绝，超时不重复执行 |
| 4 | 补齐用户已明确的功能差异 | 串口 AI、滚轮跟随、仪器通道平铺、报告正文证据链接逐项对照旧版通过 |
| 5 | 工程/插件/报告完整工作流 | 真实 5/20/500 项均按实际数量展示；配置往返、预检/运行/停止、报告限值及证据完整一致 |
| 6 | 解析与性能对照 | 真实协议样本、源文件和大日志结果一致；连续采集与缩放的延迟、CPU、内存及丢失有数据 |
| 7 | 全页面桌面验收 | 无数据/有数据/错误/长文本均检查，1100×720、1440×900、1920×1080 及 100/125/150% DPI；主题和语言与既有能力一致 |
| 8 | 五轮与交付 | 每轮均覆盖全功能，再突出专项；问题关闭并回归后才进入 EXE 预览或用户确认的完整离线包流程 |

阶段退出标准：不再依赖“按钮存在”判断完成，而是以用户从工程、配置、设备操作、数据采集到报告证据的完整流程为准。旧版已稳定的解析器、判定规则、设备命令和目录兼容保持复用；本轮不引入与迁移目标无关的整体重写。
