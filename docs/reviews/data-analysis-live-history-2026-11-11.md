# 数据分析实时图表全程显示与历史回看评估

日期为 2026-11-11。评估对象为 WiParse 1.2.2 当前 egui 工作树。方法为检查串口数据交接、帧提取、曲线存储、绘图、缓存和 AI 统计代码。前五节保留修改前的评估，第六节记录实际实现及验证范围。

## 一、为什么现在看起来像 FIFO

| 层次 | 当前实现 | 用户看到的结果 |
|---|---|---|
| 实时视窗 | 自动适应时，横轴左界取“总帧数减最近 80 帧”，右界取最新帧。例如累计 1000 帧时，自动显示第 920～999 帧（代码按 0 起算）。 | 即使全部点仍在内存，左侧历史也会不断移出屏幕。这是常规采集中最先出现的问题。 |
| 曲线存储 | 每条实时曲线分别保留最多 200,000 个有效点，超限后从向量头部删除；帧计数仍继续增长。 | 超限后，平移或点击适应也不能从当前曲线找回最初的点。字段稀疏时，不同曲线丢失历史的时刻不同。 |
| 接收覆盖 | 实时分析游标落后于串口保留起点时会前移；首次接入且游标仍为零时，有超过 2,000 行会从最近 2,000 行开始。带帧头模式的未完成文本也有大小保护。 | 全程显示只能覆盖实际收到并成功提取的范围。晚加入、缺行和提取失败需要区分；已有源日志可用于另行回放。 |
| 绘图与缓存 | 已有按可视宽度进行最小/最大值降采样的路径。新帧会使显示缓存失效；达到 64 个新增帧的刷新门槛时，当前路径构造 WIDA 快照并同步保存。 | 直接取消点数限制会放大全量坐标映射、内存复制和快照写盘开销。快照包含当时保留的数据，无法充当完整的追加式历史。 |

文件加载后已有一次全图适应，AI 导入的数据还可能使用秒作为横轴。80 帧的移动窗口属于实时串口分支，调整范围应集中在这里。当前工具栏「适应」会关闭实时自动适应，也需要一起修正，否则用户手动回到全图后，新增数据仍可能跑出视窗。

## 二、建议的交互

1. **默认全程显示。** 左界固定在本次分析的起始帧，右界随最新已处理帧增长。举例：100 帧时显示 0～99，增加到 1,000 帧时显示 0～999。各曲线共享横轴。新旧样本按相同的线性比例压缩，保留真实的间隔和事件先后关系。
2. **手动回看。** 用户拖动或缩放横轴时固定当前视窗，接收、解析和存储照常进行。新数据不把用户拽回末尾。点击「全程」立即回到起点至最新帧，并恢复自动扩展。「最近」可保留原 80 帧行为，供观察瞬态时主动选择。
3. **保留现有纵轴控制。** 原有电压、电流、温度的单位、比例尺和偏移继续生效；用户只调整纵轴时，横轴仍可继续跟随全程。窄屏可用一个视图选择控件呈现当前模式。
4. **总览与精读。** 窗宽只有 1,200 像素时，无法逐点分辨数百万个样本。总览应覆盖全部时间范围并保留尖峰；放大某一区间后显示原始提取点，光标读数、导出和 AI 统计使用原始值。缺失区间断线并注明范围。

## 三、方案选择

| 路径 | 能解决什么 | 代价与边界 |
|---|---|---|
| A．仅改实时视窗 | 小范围修改即可解决 80 帧后历史移出屏幕，以及「适应」不能持续跟随。 | 只能显示仍在内存的历史，超过 200,000 个有效点仍无法精确回看。适合作为第一批交付。 |
| B．视窗全程扩展，所有点常驻内存 | 实现简单，短时间内可精确回看。 | 内存随时间增长，全量重映射和快照保存负担随之增长，不适合连续测试。 |
| C．视窗全程扩展，最近原始点驻内存，旧原始点分块落盘，图上按像素取摘要 | 能同时满足长期全程总览、历史局部放大和精确读数。 | 需要后台写入、索引、增量统计和恢复逻辑。建议作为最终架构。 |

**建议 A 先交付，C 完成后再验收“整个会话可精确回看”。** 若产品只要求在 200,000 点以内看全程，A 可独立使用。按用户提出的长时回溯目标，应规划 C。

## 四、架构和影响范围

- **存储。** 以采集会话、串口来源及提取规则版本标识数据。按块追加帧序、各字段原始值和有效位图；使用有界写入队列、后台 I/O 和确认写入位置。磁盘空间不足或队列持续积压时，向用户显示受影响的范围。避免阻塞串口线程或把未落盘的数据标成已归档。
- **显示。** 复用现有最小/最大值降采样思路。为已封存数据块维护分层摘要，记录首点、末点和极值所在位置，按原始次序绘制。新增数据只更新尾块及其上层摘要；平移和放大时只读取可见区间，加上相邻边界点。异步读取绑定视图版本，旧请求完成后不得覆盖新视窗。
- **统计、导出和 AI。** 明确“全会话”“当前视窗”“已保留区间”的统计口径。全程计数、均值、有效率以原始值累积；导出按块顺序读取。AI 的完整性和来源字段必须反映真实覆盖。不能把绘图桶的统计当成原始样本统计。
- **兼容。** 保留串口日志原有行数限制、实时告警、文件分析和 AI 导入横轴语义。旧 WIDA 保持可读；仅含末段的旧文件不能补造早期点。切换串口、修改分帧规则或清空会话时明确划分历史，避免把两个测量条件下的曲线连在一起。
- **容量估算。** 假设 8 个字段每帧都有值，沿用每点两个 f64 的表示，100 万帧的原始坐标约为 128 MB（十进制），尚未计入显示映射、容器和快照。若采用共享帧轴，8 路每秒各 1,000 个 f64，单是数值约为 230.4 MB/小时，另有索引与元数据。磁盘预算、写入吞吐和保留期限应据实测配置；长期精确回看受可用存储空间限制。

## 五、验收方法

| 场景 | 应观察到的结果 |
|---|---|
| 1、79、80、81、1,000 帧连续增长 | 全程模式首帧始终可见，最新帧进入视窗；一帧时横轴有效；最近模式保留移动窗口。 |
| 手动放大早期 10 帧，再追加 1,000 帧 | 横轴位置和光标读数稳定；点击「全程」后首尾同时可见，后续继续扩展。 |
| 8 路、每路超过 200,000 点，头部注入一个单帧尖峰 | 总览可见尖峰；放大后帧号和值与源数据一致；GUI、导出、AI 统计的有效点数一致。 |
| 字段稀疏、启动前已有日志、串口丢行、规则切换 | 曲线共用真实帧轴，缺口和会话边界可辨；无数据区间不能被解释为零。 |
| 慢磁盘、空间不足、异常退出、重开工程 | UI 继续响应；已提交块可恢复，对未写入区间有明确提示。 |
| 性能对比 | 固定同一台机器、输入速率和画布宽度，记录现版与候选版的 UI 帧耗时 P95、接收到可见的延迟 P95、峰值内存、队列积压和每小时写盘量。建议用 1 路与 8 路分别回放百万帧；冷热区均检查，先建基线再定发布门槛。 |

## 六、实现与验证记录

实时采集默认使用全程横轴。拖动或缩放横轴后可以停留在历史区间，点击「全程」恢复跟随。「最近 80 帧」保留原有的末段观察方式。串口缓冲区已经淘汰的日志无法恢复，工具会显示缺失行范围，并从可用数据开始新的分析段。

当前会话按每路 8,192 个有效点封块。总览使用有序的首点、极值和末点，细节、光标、CSV 导出和 AI 统计读取原值。后台线程将完整块转为文件映射，并在 SQLite 事务内追加新增点与会话元数据。实时缓存扩展名为 `.widalive`，原有 `.wida` 文件仍可打开。正常退出时等待最后一次提交，异常退出后可恢复到最近一次成功提交。分块临时文件和工程缓存都会占用磁盘空间。导出 CSV 以点击时的样本为界，包含帧号、曲线名、单位和原始值。

验证使用生成的 8 路数据，每路 200,117 点，并在第 17 帧设置单帧尖峰。测试核对了全程总览、早期局部放大、光标、AI 逐路计数与最大值、CSV 行数与尖峰值，以及追加第 200,118 点后重新打开缓存的首段和末段数据。另有用例覆盖 1、79、80、81、1,000 帧的视图边界、手动回看期间继续接收、串口切换与接收缓冲区丢行。这些验证采用合成输入；真实硬件长时间采集的延迟 P95、工作集峰值和磁盘耗尽情形尚未实测。
