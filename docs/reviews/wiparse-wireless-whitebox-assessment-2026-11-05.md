# WiParse 集成测试与无线充电研发白盒测试系统评估报告

日期：2026年11月5日。

补充评估：同日再次核查无线充电执行器、自动化服务能力声明及 FPGA 宿主资源交接实现，并增加研发闭环、测量可信度和接口验收细则。补充部分属于源码审查与设计建议，未新增实机验收。

评估结论：建议继续基于 WiParse 建设无线充电研发白盒测试系统。当前最有价值的资产是仪器控制、串口与协议观察、配置工作区、可追溯运行和插件扩展机制；主要短板是实物测试闭环、原始证据完整性、跨设备同步和面向产品的白盒语义。适合从单 DUT 的辅助定位与受控回归开始建设，尚不具备直接宣称完整自动白盒验证系统的依据。

本次定位为研发测试。保持单 DUT、单工位串行执行，不引入多 DUT 并发、MES、电子签名或量产节拍作为首期要求。用户输入是 DUT 身份的权威来源；自动读取固件和芯片信息作为交叉核对，发生冲突时提示确认并保留记录。

## 1 评估基线与证据范围

源码基线为当前工作区 WiParse 1.2.2，HEAD `fa62efe`。发行参考为 `dist/WiParse-1.2.2-Windows-x64-20261105-5-Full/release-manifest.json`，其中 FPGA 固件测试插件为 0.5.5，示波器串口监控为 0.7.1，无线充电自动检验为 0.1.1。

抽查发行包中的无线充电插件 manifest、live 门禁实现、FPGA 宿主适配器，与工作区对应文件 SHA256 一致。这支持关键能力边界判断，不代表所有发行文件与源码逐一核验。此轮没有启动发行 EXE、连接仪器、运行 DUT 或执行新的完整构建。

本次重新执行两组针对性回归，共 47 项通过：

- 无线充电插件与 FPGA 宿主适配器 29 项：离线正常/失败/缺测/坏质量、live 阻断、取消后保留失败、超时不盲重试、日志游标一致性、接口与资源交接等。
- 工程配置、工作区和 runner 18 项：共享作用域、revision/hash 冲突、快照冻结、旧结果隔离、500 项、事务与进程中断恢复、预检过期阻断等。

上述是软件行为验证，测试中的模拟仪器和量测不构成真实硬件测量验收。旧设计文档只用于理解需求，不将其中拟议接口计入当前实现。

## 2 总体适配判断

| 目标用途 | 当前适配程度 | 判断依据 |
|---|---|---|
| 人工辅助研发与故障抓取 | 基础较好 | 已有仪表控制、串口触发、截图、源波形、协议分析与报告入口 |
| 固件冒烟与确定性回归 | 有条件可用 | FPGA 配置与执行框架较完整；需按具体设备、绑定和复位流程做实机验收 |
| 无线充电规则离线验证 | 已有可用基础 | 无线充电插件可 dry-run/replay，保留质量、覆盖与失败原因 |
| 无线充电实物自动闭环 | 关键能力待接通 | 无线充电插件明确拒绝 live；独立服务未统一接管仪表输出和采集武装 |
| 内部变量与电气行为关联 | 需要重点建设 | 通道与调试入口存在，但缺少产品变量字典、事件契约和可信统一时间轴 |
| 长稳、偶发问题与跨固件统计 | 局部可复用 | 循环与证据目录可用，完整流式质量、持续恢复和统计比较尚不足 |
| Qi 正式认证 | 不属于当前系统能力 | 自研研发测试可用于预验证，正式认证有独立的合规与互操作流程 |

“白盒”的必要条件是能观测产品内部状态，并将外部刺激、内部响应与独立电气测量关联。拥有 DAP、I2C 或日志窗口只是接入条件。当前也不能从集成测试通过率推导固件语句、分支或条件覆盖率；代码覆盖率需要额外插桩、映射和采集链路。

## 3 当前优势

### 3.1 平台基础值得保留

Testing Hub 已有插件生命周期、预检、配置仓库、矩阵和证据导航。无需重新开发一个平行测试平台。GUI 负责操作体验，插件负责产品场景，宿主负责设备与文件接口，这个方向适合长期演进。

配置工作区提供 schema 校验、可视化编辑、导入导出、revision/hash、原子事务和运行快照。工程共享配置已在 FPGA 路径中承载基本信息、DUT 约束及仪器绑定，测试项可引用角色。这能减少重复配置，降低“改了配置却以为仍在测试旧配置”的风险。

矩阵支持实际测试项与最多 500 项配置；配置变更、旧结果、当前执行和复测 attempt 有分离机制。对研发来说，保留某次失败时的原始配置比仅保留最终 PASS 更有价值。

### 3.2 观察手段与问题定位接近需求

已有示波器、直流源、负载、万用表，以及 UART、Dongle 和调试桥接入口。串口触发抓取适合“出现指定异常时留下现场”。原始波形入口、协议解码与报告链接为追查电气和固件交互提供了基础。

自动化核心已有电压统计、阈值边沿、burst 周期分析和双向死区分析；死区路径要求 raw、同步采集、capture ID 与 deskew 元数据。还存在带质量标记、单位、不确定度、限值引用及 guard band 的判定结构。因此不足是端到端接入和验证，不能笼统说“没有波形算法”。

### 3.3 结果真实性边界已有正确基础

无线充电插件区分执行成功、回放验证结论和产品结论，模拟正常库不会给真实 DUT 出具 PASS。缺测、坏质量和空检查集合不自动通过；已经确认的失败不会被后续取消或执行异常抹掉。这些机制应保留并统一到后续无线充电实物路径。

## 4 主要缺点与架构风险

### 4.1 产品编排与通用服务之间存在断层

`wireless-charge-validation` 0.1.1 只有 preflight/run/stop，未声明新版 configure、test_matrix 或 project_config。其产品、限值、状态、工位、catalog 和 scenario 仍主要是插件目录中的版本化文件。

这意味着新版 Hub 和 FPGA 的可视化配置、工程共享与矩阵能力，不会自动出现在无线充电插件中。需要明确迁移，不应要求研发人员回到源码编辑，也不应把无线充电场景硬塞入 FPGA 插件。

**影响：** 宿主能力看起来齐全，产品插件仍可能停留在离线演示与旧表单层。

### 4.2 设备控制存在多条管理路径

FPGA 宿主适配器通过 GUI HTTP API 控制仪器、交接串口、等待事件和归档；独立 WiParse-Service 提供分析、判定、UART 采集和自身 lease。

服务 `system.capabilities` 明确声明仪表仍归 GUI 所有，`instrument.output.control`、`scope.armed.verified`、`dongle.capture.binary` 和 `protocol.streaming` 未支持。FPGA 的锁和服务 lease 不是已经统一的全设备资源管理体系。

**影响：** 单工位仍可能发生手动页面、插件与后台服务对同一设备的竞争。需要一个设备权威所有者；短期可由 GUI 宿主统一承载，长期可迁入服务。必须保持兼容适配，不能让两条路径同时独立发命令。

### 4.3 当前日志实现不能等同原始字节与准确事件时间

`fpga-host-adapter.mjs` 的 `collectLog` 从 `log.lines.get` 轮询文本行，再补换行并用 UTF-8 重新编码为 `raw_base64`；行时间为读取时的 `performance.now()`。

这能保存可读日志，但无法证明保留了原始 CR/LF、编码错误、非文本字节和真实接收时刻。当前针对性测试证明编码结果与所建游标范围一致，并未证明它等于串口线路原始字节。

**影响：** 可用来证明“观察到某条日志”，不足以直接证明“某时刻硬件已经响应”。必须分开保存原始接收字节、解析文本、设备时间和主机接收时间，并记录丢字节、断流及时间质量。

### 4.4 定时抓取不等于精确同步采集

现有 adapter 的 `capture` 获取截图，`waveformSource` 另行读取源波形；这两个方法自身未提供统一 armed/capture session 与同次采集证明。服务已有时间映射算法，但没有端到端设备同步验证。

对启动、保护和偶发事件，应先确认示波器武装，再施加刺激，并使用预触发记录、硬件标记或经验证的时钟映射。串口关键词出现后再抓取，不能保证保存了此前短暂的异常。

复位释放作为既定计时起点可以保留，但要区分“命令返回时刻”和“实际复位释放时刻”。DC 电源输出打开也不等于 MCU 已脱离 POR；需要按产品选择复位脚、电源阈值或启动标记作观测依据，并记录误差。

### 4.5 白盒信息尚未形成产品契约

需要统一描述固件 build ID、变量/寄存器地址、位域、类型、单位、缩放、采样周期、状态码和访问副作用。编译后地址变化、读清状态位和高频调试读取都可能影响测试对象。

建议以非侵入结构化遥测为主，寄存器读取为补充，DAP halt 为明确的调试操作。内部反馈值、控制目标值和独立物理读数必须分列；不能因固件自己打印“电压正常”就完成电压验证。

### 4.6 安全停止与异常恢复仍需产品化

当前 adapter 的 cleanup 主要发送配置的电源关闭指令；指令完成不自动证明桥驱动停止、负载处理正确或残压已消失。取消与等待任务收敛有可复用实现，但不能因此推导已具备无线充电物理工位安全闭环。

需要按产品定义停止顺序、状态读回和恢复入口。无响应、USB 拔出、进程退出等情况下，独立硬件限流与保护继续有效。软件控制保护和测试判定要分开；用于研发也应避免异常后自动重复施加未知刺激。

### 4.7 配置规模不等于试验规模

500 是配置数量限制，不是 500 次循环、500 台设备或 500 个组合的统一上限。适配器、线缆、RX、位置、温度、固件与负载组合会迅速扩大。

应将“场景模板”和“本轮展开的试验实例”分开。允许一个模板生成多个实例并串行调度，运行前显示组合数和预计时间。一般组合可压缩，高风险边界与历史缺陷组合明确保留。

### 4.8 运行界面与研发分析仍需整合

既往截图中的大表单、内部字段暴露和重复配置，说明通用 schema 不足以直接生成易用产品界面。当前配置声明与布局已有改进，但本轮没有对最新 EXE 做视觉复验，不能据旧截图断言最新页面完全未改。

应围绕工程设置、测试配置、执行矩阵和结果分析组织操作。选中测试项后，右侧集中显示结果、失败依据及证据；需要编辑时进入明确配置区域。运行页面不堆放模型设置、底层 selector 和完整规则树。

## 5 无线充电白盒测试需求与差距

以下以 TX 为首期对象，RX 产品另设配置，不把 TX 的桥压、驱动与状态机强套给 RX。

| 测试领域 | 必需的内外部证据 | 当前可复用 | 必须补齐 |
|---|---|---|---|
| 启动与复位 | 复位原因、启动状态、VIN/VBRG、首个 PWM | 日志、复位、波形与循环框架 | 实际 t0、采集先就绪、启动事件关联 |
| 状态转换 | 内部状态、转换原因、Qi 消息、电气功率 | 状态规则及串口协议观察 | 产品状态字典、实时窗口、非法转换证据 |
| 功率调节 | 目标/反馈 VBRG、频率、占空比、负载与物理读数 | 电源/负载接口与基础量测 | 动态刺激、响应时间、稳态窗口与同步采样 |
| 桥驱动与死区 | 四路 VGS、对应换向、deskew、桥节点/电流 | 原始波形与离线死区算法 | 同次多通道采集、探头校正及算法实测对照 |
| Qi 通信 | CE/RP/EPT、重试、时序与独立协议证据 | 日志消息与部分离线解码 | 目标协议版本语义、持续覆盖、完整计数分母 |
| 输入协议与适配器 | 合同、板端输入、掉电和重协商 | PD/SCP/UFCS 等分析入口 | 真正协议源/适配器控制；被动解码不能替代主动模拟 |
| 保护与恢复 | 故障注入、保护码、停桥、残压与恢复 | 限值判定、错误与清理框架 | 产品特定注入、反馈闭环与恢复验收 |
| FOD | 估算损耗、校准参数、输入/输出功率、测试物与温升 | 数据与报告基础 | 可控 RX、测试夹具、校准与误报漏报验证 |
| 效率与热 | 同边界功率、温度位置、环境与稳态条件 | 基础电压电流与报告 | 同步功率、温度接入、不确定度及稳定段识别 |
| 长稳与偶发故障 | 原始事件流、首个故障、环境与中断记录 | 循环与独立 attempt | 分块落盘、断流质量、长时资源恢复与统计 |
| 固件 A/B 回归 | 同产品配置、工况、算法、样本与版本 | 快照与结果元数据 | 跨运行对齐、分布与离群点、重复性分析 |

手机适合真实兼容性场景；可控 RX 适合可重复量测。未获得可靠电池遥测时，不能仅凭 TX 输出推断手机电池 CC/CV 状态。

FOD、效率与热表现与最终线圈、屏蔽及结构有关。TI 的 RX 调试文档分别讨论启动、效率、热与 FOD，并强调最终结构下的调谐和校准；该资料用于说明测试维度，不把其中旧器件或协议数值当成当前所有产品限值。[TI 测试与调试无线电能接收器](https://www.ti.com/lit/an/slua724/slua724.pdf)

## 6 建议目标架构与拓展方式

推荐保留现有 Hub 和独立无线充电插件，增加通用设备协调、产品白盒契约和统一证据服务。各层关系为：

`Testing Hub 操作与矩阵 → 无线充电场景插件 → 通用设备与任务协调 → 仪器及 Dongle → 统一证据与分析 → 规则判定与报告`

| 层次 | 职责 | 应避免的问题 |
|---|---|---|
| Hub | 工程、可视化配置、预检、串行队列、矩阵、结果导航 | 不写 Qi 状态机、产品寄存器地址或具体保护阈值 |
| 通用宿主/服务 | 唯一设备所有者、资源锁、超时、武装/完成反馈、采集会话、持久化 | 不让每个插件重复发明串口、租约和时间戳体系 |
| 无线充电插件 | TX/RX 产品配置、测试场景、步骤编排、状态规则、覆盖与报告摘要 | 不直接绕过宿主访问 USB/VISA，避免复制 FPGA 执行器 |
| 白盒适配层 | 遥测、变量/寄存器字典、固件版本匹配、受控写入 | 不用不同固件的旧地址读值并当作有效数据 |
| Dongle | UART/I2C/GPIO 等实际支持的采集、设备标记和健康数据 | 不把未来规划的同步/带宽/故障注入写成现有能力 |
| 分析与证据 | 原始文件、来源/时间/质量、版本化算法、重放与重判 | 不用截图或 UI 降采样曲线替代精密量测输入 |

短期无需重写整个服务。先定义一个稳定的通用设备接口，将现有 GUI adapter 封装其下；无线充电插件通过同一接口执行。随后按设备迁移到服务，保持插件不感知底层归属变化。

新增硬件能力要按设备型号、固件、驱动版本做能力表和实机验证。品牌名称或 driver 类型不足以证明满足采样点数、同步、动态输出和触发要求。

## 7 配置与判定设计建议

工程共享保存 DUT 身份约束、仪器角色、通道/探头映射、遥测字典和默认采集策略；产品 profile 保存拓扑、状态机与适用测试；测试项仅配置刺激、观测、窗口和判据。运行实例额外记录实际输入身份、固件、连接身份及环境。

测试项建议采用可视化步骤：准备 → 武装 → 刺激 → 等待条件 → 采集 → 数据质量检查 → 判定 → 清理。支持条件等待和 deadline，避免全部依靠固定 sleep。沿用“多波形任务资源重叠时预检阻止执行”的既定策略。

矩阵状态与产品结论应分层：TBT、TESTING 表示执行进度；完成后显示 PASS、FAIL、无法判定、跳过或执行异常。若外层保留四种主状态，也必须在详情明确区分缺测与实际超限，不能把所有异常包装成 DUT FAIL。

研发限值允许修改后立即用于后续运行，不强制引入电子审批。保存新 revision 并使预检失效；每份报告显示实际使用的上下限、单位、窗口、规则/算法版本与修改后版本。历史结论保持原样；重判生成关联的新分析记录，保留新旧差异。

自动化核心目前存在 `approved` 限值门禁，而研发即时修改是既定需求。应明确该字段的研发语义及规则映射，区分“研发有效配置”和“正式产品批准”，避免一个布尔值同时承担两种含义。不能为了开放研发限值而删除真实质量和安全门禁。

原始事件至少关联 run、item、attempt、DUT、固件、设备/通道、采集会话、时间来源与误差、质量标记、原文件 hash 和算法版本。丢数据、失同步、量程削顶和不支持测量要显式传播为无法判定。

AI 放在全局设置中，由测试项选择是否辅助分析。适合做异常摘要、相似历史检索和定位建议；数值判定与保护执行仍由确定性规则处理。公网模型按授权字段白名单与脱敏策略外发，记录模型、提示模板和输入证据版本；模型不可用不影响原始证据归档与基础判定。

## 8 实施优先级与责任范围

以下是建议的责任分工，未在本次评估中向其他工位发送开发指令。

| 优先级 | 工作 | 主责 | 协同及完成条件 |
|---|---|---|---|
| P0 | 设备唯一所有权与通用接口 | 软件工程 | 插件开发接入；手动页面/插件/服务争用时明确阻断 |
| P0 | UART 原始流、游标和时间质量 | 软件工程 | Dongle 提供硬件信息；二进制及换行测试可逐字节重放 |
| P0 | armed、采集会话及复位起点 | 软件工程 | 插件定义场景、硬件验证标记；用独立波形测量实际延迟与误差 |
| P0 | 无线充电插件迁入新版配置/矩阵 | 插件开发 | 软件工程只补通用组件；全部测试项可列出、选中查看详情 |
| P0 | 首期产品遥测和白盒字典 | 固件/产品负责人 | 插件接入；build 不匹配或必需变量缺失阻断对应项 |
| P0 | 产品停止顺序和反馈 | 产品/测试负责人 | 软件与硬件实现；断连/取消/进程退出有明确结果和恢复方式 |

| P1 | A/B 比较、趋势和试验实例管理 | 软件工程 | 插件提供产品维度；能按同工况比较固件回归 |

不应由插件修补通用日志字节或 GUI 布局底层问题，也不应由软件工程在 Hub 内硬编码产品限值与 FOD 场景。先冻结公共接口及数据格式，再并行实现各自模块，可减少重复修改。

## 9 分阶段建设与验收

### 阶段一 单产品观察与复现

选定一种 TX、一个明确固件版本、一台示波器和固定 RX。先打通原始 UART、内部状态、VIN/VBRG 和基础源波形关联。验证人工可复现问题的自动留证。退出条件：已知问题的证据可回放，版本与通道无歧义，缺数据不放行。

### 阶段二 二十项实物回归

建议首批 20 项如下，每项包含刺激、内部证据、独立物理证据和判据：

| 编号 | 场景 | 关键验证 |
|---|---|---|
| 01 | DC 冷启动 | 实际启动起点、复位原因、VIN/VBRG 与首个 PWM |
| 02 | Dongle 复位 | 实际释放标记、重启路径及日志连续性 |
| 03 | 无 RX 待机 | 状态、扫描行为与空载功耗 |
| 04 | RX 放置 | PING 到识别/配置/PT 的状态和功率关联 |
| 05 | RX 移除 | 退出原因、停桥和停止后残压 |
| 06 | PING burst | burst 内频率、持续和间隔，排除空闲段 |
| 07 | 低功率稳态 | 状态、控制目标与实测值一致 |
| 08 | 额定工况稳态 | 电压、电流、频率与限值 |
| 09 | 负载阶跃上升 | 调节轨迹、超调和恢复 |
| 10 | 负载阶跃下降 | 退载过冲、控制与恢复 |
| 11 | 输入欠压 | UVLO 原因、停桥和恢复 |
| 12 | 输入中断与恢复 | 断电事件、重启与异常循环 |
| 13 | 输入限流 | 降额策略、功率预算与状态 |
| 14 | 通信超时 | 超时原因、退出与恢复，需可控 RX |
| 15 | 正常 EPT | 正常结束原因不误判故障 |
| 16 | 温度降额 | 温度来源、阈值/滞回与功率；注入和实温分开标注 |
| 17 | 桥臂 A 驱动 | H→L 与 L→H、实际 VGS 与同步质量 |
| 18 | 桥臂 B 驱动 | 两方向死区、跨桥关系及证据 |
| 19 | 可重复 FOD 场景 | 校准状态、测试物、保护原因与响应 |
| 20 | 历史故障复现 | 已知失败条件、首个异常与复测对照 |

暂不具备刺激设备的项目显示缺少能力，不用模拟 PASS 补齐实物验收。二十项是首期方案，具体工况和限值由产品确定。

每项设置正常、明确失败和缺测/坏质量路径；保护性测试先在可控工况下完成工位确认。比较自动结果与人工分析，记录误判、漏判、量测差异和重复性。验收同时覆盖仪器断连、串口中断、磁盘不足、取消和进程退出；新 attempt 不覆盖原失败。

### 阶段三 回归与定位分析

增加固件 A/B、重复试验分布、状态驻留时间、失败聚类与首次异常时间线。若宣称长稳，必须实际运行目标时长并验证持续落盘、断流和恢复；现有名为 soak 的回放 suite 不构成长稳实现。

### 阶段四 工况扩展

再纳入真实适配器/线缆、温度、偏移、更多 RX 与 RX 产品测试。按产品声明的协议版本、功率与拓扑扩展，不将某个器件示例的频率、死区或功率固化为平台默认限值。

研发自测与正式 Qi 认证分别管理。WPC 当前流程要求授权实验室的合规测试及互操作测试中心测试；WiParse 可提供研发预验证与问题证据。[WPC Qi 认证流程](https://www.wirelesspowerconsortium.com/knowledge-base/testing-and-certification/qi-certification-process/)

## 10 反对意见与决策建议

不建议把“继续增加插件和配置项”作为主要建设路线。设备时序、原始数据与共享所有权没有解决时，更多测试项只会产生更多难以信任的结果。

不建议重写全部平台或立即追求量产体系。现有配置、矩阵、证据与仪器基础可复用；研发阶段先解决一个产品、一套工位、二十项真实回归，比先建设多工位调度和电子签名更符合当前目标。

不建议把测试日志、协议报文和固件内部自检视为相互独立的正确性证明。它们可能来自同一错误数据源，应以物理测量和可控刺激补充交叉验证。

不建议把 AI 自动判定作为首期差异化核心。对研发最有价值的是“能重复制造问题、准确留证、说明为什么失败”。AI 可建立在这些可信证据之上。

建议批准单 DUT 的研发验证建设方向，优先投入统一设备管理、原始流与时间质量、产品白盒契约，以及无线充电插件的实物闭环。先完成首期真实测试验收，再扩大测试矩阵与设备范围。

## 11 补充评估：研发工作流和能力依赖

研发人员的实际工作通常从一次异常开始：识别板卡与固件、复现现象、定位第一次偏离、修改后在同一工况复测，最后和历史版本比较。因此平台的最小闭环应当让工程师在同一个测试工程内完成：输入 DUT 身份 → 选择产品配置和工况 → 检查仪器和探头 → 武装采集 → 测试与记录 → 查看首次异常附近的内部状态、日志和波形 → 复测或对比。

当前 Hub 在配置、运行与报告方面提供了基础，但无法仅凭现有无线充电插件把上述流程自动贯通。特别是其 replay 使用明确标记的模拟 fixture；虽然规则调用真实的 `check.evaluate`，量测并非来自当轮实物。测试报告应始终展示数据来源：实测、导入、模拟或人工输入，以及其是否满足该测试的证据要求。

建议以以下依赖顺序组织实施；这些依赖可以由不同责任人并行准备，交付必须按接口验收衔接：

1. **固定样机和工位边界。** 确定 TX 拓扑、固件、可观察节点、RX、供电、探头和独立保护，形成版本化工位清单。产品不支持的项目标记不适用，不能填入示例限值冒充可测。
2. **确认设备控制和数据来源。** 每一资源在同一数据根下只有一个权威控制入口；识别设备型号、序列号、固件与能力，命令超时后通过读回确认状态。
3. **建立原始数据和时间关系。** 测量原始 UART 和波形完整性、硬件标记与时间误差，再建立复位、固件事件与电气边沿的关联。
4. **定义产品语义。** 固件提供状态、原因码和采样字典；配置定义单位、标度、访问副作用与版本兼容，明确内部值和独立物理测量的关系。
5. **接入单项实物闭环。** 优先打通冷启动和已知故障复现，再扩至其他测试项；每项先证明刺激实际生效、观察完整、判定可复核。
6. **扩展矩阵和分析。** 数据可信后再推进批量组合、A/B 趋势与长稳；避免用测试项数量替代有效覆盖。

### 11.1 设备锁的实际边界

FPGA 适配器使用工位文件锁，并将资源列表写入锁记录。其 `leaseRoot` 优先采用当前测试目录下的 `.leases`，因此不能只根据“锁文件存在”推定不同测试目录、不同数据根或 GUI 手动控制都被统一约束。独立服务 lease 在其服务状态中维护，服务重启也会产生新 session epoch。以上是源码边界；具体跨实例冲突情况需要端到端复现。

建议建立稳定物理设备标识与单一仲裁入口，明确锁的作用域、进程死亡后的设备未知态、手动控制进入方式，以及 GUI/服务/插件跨进程竞争规则。不要用不同目录的同名 station 锁推导设备互斥；首次上线时用同设备不同项目、手动操作、服务重启三组冲突试验验证。

### 11.2 可靠时间轴需要单独预算

每项测试定义目标时间分辨率和可接受误差，而不是所有事件共用一个笼统的“已同步”。分别记录：刺激实际生效时刻、设备时钟、主机接收时间、示波器采集起点、同步标记、时钟映射残差和丢包情况。异步读取的 UART 时间只能在已测得的延迟区间内解释；设备重启、时钟回绕和时间映射过期均应使对应关联失效。

例如，以 GPIO 同时进入示波器与 Dongle 采集，重复测量它们相对边沿的偏差与抖动，建立该工位的误差预算。若预算大于某项保护响应的允许判定裕量，该项需要更可靠的硬件触发或更高分辨率；不能仅靠插值或调整判定限值弥补。

### 11.3 测量结果可信度与覆盖率

对每个关键量给出测量点、探头类型及倍率、量程/带宽、采样率和有效样本、时间窗、校准与连接方式。桥臂高侧判定使用相对源极的 VGS，比较双方向死区前验证通道同步与探头延迟。电压削顶、通道错配、采样不足或无法确认采集来源时，结果为无法判定。

效率明确输入与输出边界以及同时测量的时间窗；需要时计算平均瞬时功率，记录电压电流通道相位误差。FOD 要保留接收端类型、位置、异物和产品结构，识别温度/功率变化对结果的影响。单次通过不足以证明该场景覆盖了位置、对象及温度边界。

覆盖率至少分成三类：**计划覆盖**（已设计场景/应覆盖场景）、**执行覆盖**（完成且证据合格的场景/计划场景）、**结果分布**（PASS、FAIL、无法判定及跳过的数量）。报告展示分母和筛选条件；缺测或跳过不能算作成功执行，场景覆盖也不代表代码覆盖。

### 11.4 内部遥测可能改变被测行为

白盒信息会增加串口带宽、CPU 负载和中断压力，读清寄存器或调试暂停还可能改变状态。每个采集方式需标识只读性、副作用和理论上限；比较遥测开启与关闭时的启动时间、异常出现率和关键波形。无法证明不影响结果时，将该测试标记为带观测干预，不能直接与无干预版本混合比较。

### 11.5 资源与实施范围取舍

首期固定一款 TX、一个可重复的 RX、有限仪器型号，优先支持启动、状态转换和一个历史故障，可控制对设备和算法的依赖。借助人工更换 RX、人工记录位置可以先完成辅助回归，但必须在报告标识人工步骤；因此复现效率与位置重复性仍受人员影响。

若目标是无人值守的 FOD、复杂适配器异常和长稳，需要额外可控设备、夹具及联锁，也需要固件团队提供稳定遥测。没有这些外部条件时，软件可以完成数据接入和分析开发，但不能独立完成相应实物场景。工期与预算应在产品清单、现有设备和人员投入确定后估算，本报告不编造进度或采购成本。

## 12 补充验收契约与优先决策

| 交付点 | 可执行的验收方式 | 通过条件 |
|---|---|---|
| UART 原始流 | 用已知二进制序列包含 CR/LF、无效 UTF-8、分包与断连；从输入源和归档逐字节对比 | 字节一致；人为丢失、截断、断连被标记，不能报告完整 |
| 设备所有权 | GUI 手动操作、两个项目和后台服务同时请求同一真实或可控模拟设备 | 至多一个控制者；冲突清晰提示；中断后状态未知时阻止新刺激直至确认 |
| 采集时序 | 分别验证采集未武装、武装后刺激、仪器超时与采集完成；同步信号反复测量 | 未武装不得施加自动刺激；结果保留同次采集标识和测得的误差 |
| 产品白盒字典 | 使用两个固件版本和含副作用的寄存器案例 | build 不匹配或未声明副作用时阻断相关读取；版本、单位、缩放可追溯 |
| 实测判定 | 金样、已知异常样、缺通道、削顶、窗口缺失与限值边界 | 观察到的失败保留；坏质量和缺测不能 PASS；报告显示实际限值和证据 |
| 中断恢复 | 分别模拟串口掉线、仪器断线、磁盘不足、停止及进程退出 | 保存已完成证据和首个异常；未确认安全状态不自动重试；新 attempt 不覆盖旧数据 |
| 研发体验 | 导入真实测试配置并由工程师完成选择、运行、查找失败和复测 | 全部测试项可见；选中后可查看该项依据；常规操作不需要编辑源码 |

上述验收的次数、误差阈值与代表设备清单应由产品和测试负责人在工位确定后给出；先建立测量方法，再以数据批准阈值。自动化回归可证明协议和错误处理，设备一致性、延迟、数据质量与物理保护必须分别做实机验证。

建议下一步先明确五个项目输入：TX 或 RX 产品及功率拓扑、首期固件与可用遥测、现有仪器型号和探头、可控 RX 与故障注入条件、首批最需要复现的历史问题。这些输入决定二十项中哪些能直接实施、哪些需要新增设备或降级为人工辅助。
