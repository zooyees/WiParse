# WiParse AI 任务理解、连续性与开源组件评估

2026-11-12，基于 1.2.5 的 Rust/egui 工作树。评估对象包括串口助手、工程助手和测试报告助手。这里的性能分为任务完成质量、模型往返次数、Token、响应时间及工作站开销。一次模型调用很快，也可能因为遗漏一个字段而需要整项返工。

## 从一次硬件分析任务看问题

假设操作员要求“从这次充电日志提取六个字段，显示曲线，最后保存报告”，随后补充“电流用 Iin，先别生成报告”。宿主需要区分原始测量、字段映射、绘图回执和报告文件四种事实。已扫描的日志仍然有用，旧图能证明的只有当时实际显示的字段。修正后的曲线要有新口径下的证据，报告任务应取消。设备已执行的动作还需要保留原回执。

| 问题 | 代码中观察到的行为 | 本轮处理 |
|---|---|---|
| 部分完成后的续问失去原任务 | 两个运行入口均主要依据“等待输入”判断续接。普通“继续”可能更换任务 ID、清空活动步骤，早期证据转为历史状态 | 在来源一致时处理显式续问、结果引用和修正。共享入口同时核对页面、工程与权限。同一任务保留原目标、计划和证据 ID；显式“新任务”可退出澄清 |
| 中途修正丢失实测结果 | 串口修正原先清空 Workflow、近期工具回执和证据 ID；共享入口只追加目标，旧完成状态又可能过期 | 共用修正逻辑。保留本地测量、设备执行记录，分析结论重新待核验；模型可以根据修正调整分析步骤的对象和拆分 |
| 混合问句漏项 | “如何……”的解释语气可持续影响后面的独立指令 | 分句判定。能区分“如何计算时长，绘制曲线？”和“如何导出报告？然后绘制曲线，再生成报告” |
| 多步骤只有状态，没有前置关系 | “提取、绘图、出报告”原本只能作为平行列表；宿主没有结构化信息指出哪个步骤可以先执行 | 计划可选填 depends_on。宿主给出 ready_steps，核对依赖存在、无环、前置完成。旧计划和简单问答仍可直接执行 |
| 普通队列消息被当作澄清答案 | 串口队列只检查运行中及错误状态，助手等待用户补充时也可能自动取下一条 | 等待澄清时保留队列，用户直接作答；补充处理后恢复原有顺序 |
| 本地准备上下文做重复工作 | 有重叠的页面与平台方法会重复进入原生工具枚举；证据索引按字节裁剪时反复序列化整个列表 | 工具按名称去重并保持顺序；索引从最新证据起按实际 JSON 字节一次计入，仍保存最新的完整条目，支持按 ID 取详情 |

本轮续接判断针对“继续”“基于上述”“改为”等明确表述，以及助手发出的澄清问题。未显式关联的自由提问仍可能开启独立任务。来源或设备读数跨时间发生变化时，已有证据只能说明原观测。模型对自然语言约束、别名和单位的理解仍需用真实供应商评测。

## 组件选型

| 优先级和角色 | 与 WiParse 的具体接法 | 可能改善的指标及代价 |
|---|---|---|
| 1 · Promptfoo，研发评测 | 在 CI 用自定义 provider 或回放适配器调用实际 WiParse 任务入口，导出工具名、参数、来源、回执和最终状态，以确定性断言检查结果。真实模型与固定模拟响应分组统计 | 最容易发现“文字说完成但图上少一条”“第二轮重复扫描”。主要提高回归覆盖，对桌面运行时没有直接加速作用。[断言与工具轨迹](https://www.promptfoo.dev/docs/configuration/expected-outputs/) |
| 2 · LiteLLM Proxy，可选内网模型网关 | 复用全局服务器地址和 Chat Completions 接口。用独立模型别名分别映射 DeepSeek 和 DashScope，在同一工位测试直连与代理。网关只负责模型请求，宿主掌握设备执行队列 | 在供应商限流、故障或多工位共享配额时可能改善成功率和尾延迟；正常请求多一跳，重试也可能增加费用。单供应商工位应先保留直连基线。[代理接口](https://docs.litellm.ai/docs/proxy/quick_start) · [路由](https://docs.litellm.ai/docs/routing) · [DeepSeek](https://docs.litellm.ai/docs/providers/deepseek) · [DashScope](https://docs.litellm.ai/docs/providers/dashscope) |
| 3 · Rig，可选 Rust 模型适配器 | 在现有 AiService 下用同一组消息、工具定义、取消信号及模拟服务对照。先覆盖流式增量、截断、工具调用 ID 和配对、推理字段、用量缺失及取消，再考虑替换适配路径 | 有望减少多供应商维护成本；需要测 Windows 包体、依赖、常驻内存和首 Token 延迟。具体千问端点及 DeepSeek 模型要按接口实测。[Rig 项目与库说明](https://github.com/0xPlaygrounds/rig) |
| 4 · LangGraph.js，长流程编排 | 多台工位、跨进程恢复或隔夜批量实验出现时，试验将扫描、提取、呈现、报告作为图节点。复用 WiParse 任务 ID、来源标识和操作回执；硬件动作恢复前读回状态 | 检查点有利于进程中断后的恢复。当前单机已有 SQLite 日志，增设图状态需要解决双写、恢复顺序及进程生命周期。[持久化与检查点](https://docs.langchain.com/oss/javascript/langgraph/persistence) |
| 参考 · Pi Agent 核心 | 借鉴运行中修正与后续排队分离、按工具决定顺序执行的做法。需要 Node 侧 Agent 时再比较独立进程方案 | 对解决队列时序有直接参考价值；桌面再引入一个工具循环会增加状态同步和调试成本。[Pi Agent 运行循环](https://github.com/earendil-works/pi/tree/main/packages/agent) |

## 试点和验收

1. **固定真值和环境。** 以同一合成日志、同一模型快照、输出预算、温度及权限运行不同实现。覆盖解释与执行混合、字段修正、取消报告、部分完成后续问、待澄清时已有队列、换数据源、设备动作已发送但回执未知。留一组未参与调试的字段名和问法。
2. **以工具结果评分。** 检查六字段的真实绘图回执、文件 ID、缺失样本与来源行号。分别统计全部目标正确完成率、错误完成数、重复扫描数、重复设备写入数、要求用户无效确认次数。一次错误的设备重发或跨来源引用应单独调查，不能被均分掩盖。
3. **分开测量时间和成本。** 记录首个本地证据耗时、首段可读回答耗时、整项完成耗时 P50/P95、模型往返、实际输入／缓存／输出 Token。按成功任务计算总成本时应计入失败和重试。另测工作站峰值内存、GUI 采集响应和发布体积。供应商缺报用量标记为未知。
4. **按层对照。** 先测本轮原生版与上一版；再只增加网关，对比分别直连 DeepSeek、千问时的表现；最后单独比较 Rig。首次与热缓存分组，记录失败样本和模型具体名称。真实测量结果、动态仪表状态及写操作回执按工程、对象和观测时间核验，避免语义相似的旧结果冒充新测量。
5. **发布选择。** 如果瓶颈是意图误解，投入评测语料、任务状态及交付证据；如果瓶颈是供应商限流，试网关；如果是长作业恢复，再试持久工作流。只有同场测得完成质量、延迟或成本收益且仪表流程通过回归后，才将相应适配列为默认。

## 验证范围

全工作区回归通过 688 项，按仓库配置跳过 8 项。最后针对指令否定和修正后保留无关步骤的调整，另跑工作流测试 26 项，全部通过。没有启动真实仪表或在线供应商会话。

证据索引的合成对照使用 42 条八通道回执，在最近 32 条中保留最多 16 KiB。两种算法保留完全相同的最新 11 条；按实际 JSON 编码长度计，旧裁剪过程累计处理 646,140 字节，新过程累计处理 16,380 字节。这里测量的是本地生成索引时的序列化工作量，发给模型的索引内容相同，不能换算为模型 Token 或端到端加速比例。

本轮开发直接修改 WiParse 宿主。串口模拟服务用两次用户输入、一次串口视图读取验证证据复用；同时覆盖等待澄清的队列、报告来源与权限切换、计划依赖及索引裁剪。新增组件属于技术选型，尚未随 EXE 安装，也没有把真实日志发到外部模型做对照。现有测试可以验证宿主行为，无法据此推算 DeepSeek 或千问在现场任务上的成功率、节省 Token 的比例或代理性能。
