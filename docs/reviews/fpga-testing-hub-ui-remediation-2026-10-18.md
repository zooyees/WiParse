# FPGA 固件测试配置页面整改报告

日期：2026年10月18日。面向系统架构、软件工程、插件开发与集成验收。

本报告评审用户提供的四张已交付页面截图，并对照交付 ZIP、当前 Hub 表单实现、FPGA 配置定义，以及“插件开发”工位正在进行的 0.4.0 升级。结论是：**当前配置页面仍以数据结构为组织中心，尚未形成面向测试工程师的配置工作流。三栏外壳整理没有解决内部表单问题。Hub 通用编辑器是主要技术整改对象，插件必须同时补齐业务表达，系统集成与发布承担最终体验验收责任。**

这不是颜色、边框或间距的一次局部修饰能够解决的问题。整改目标是让用户按“选择设备—设置复位—安排采集—定义判定—预检执行”完成任务，同时保留配置完整性与可追溯性。

## 二 对前次改进和验收结论的纠正

前次完成了三栏容器、最大内容宽度、工具栏与空状态，改善集中在工作区外壳。内部仍是通用递归表单，因此真实 FPGA 配置一旦展开，原有问题继续出现。

前次主要视觉证据包含简化配置与通用示例。500 项测试证明列表容量和刷新成本，并不能证明包含仪器、复位、波形及组合判定的长配置易用。包内容校验证明文件、哈希、依赖与模拟证据完整，也不能证明页面美观或操作合理。

因此，前次“视觉验收通过”“无重叠”等结论应限定为已查看的特定页面与尺寸，不能泛化为 FPGA 配置体验整体通过。系统架构与集成验收需要为这一覆盖缺口负责，不能把全部整改转交插件开发后认为已经闭环。

## 四 架构根因与责任边界

### 1 配置 schema 不等于配置界面

JSON Schema 负责有效数据类型、必填项和取值约束；它不会天然表达常用顺序、字段宽度、信息层级、编辑意图与任务步骤。当前递归渲染把 schema 属性顺序、对象嵌套和字段是否存在过度映射为页面布局。

当前 `form` 中，可选且不存在的字段被逐项渲染为加号按钮；常量字段直接输出值；数组逐个完整渲染；对象继续嵌套折叠。这四类行为可以直接解释用户截图的主要问题。给表单外增加卡片不能改变上述机制。

### 2 UI 声明与真实控件之间缺少能力闭环

插件声明了 `rule_builder`，但当前表单渲染路径没有同名专用规则编辑分支；规则仍沿联合类型和对象数组的基础路径渲染。时间轴当前能在检查面板生成预览，不能因此称已经具备完整的波形任务编辑器。

未知控件静默退回基础控件，对旧插件兼容有价值，但会使“声明了能力”和“用户真正获得能力”混为一谈。应增加 editor capabilities/version 协商：必需控件不支持时给出明确诊断，降级模式有标识，并阻止把降级效果按正式产品体验验收。

### 3 责任按照模块契约确定

| 责任方 | 必须负责 | 协作接口 | 不能作为免责理由 |
|---|---|---|---|
| 系统架构 | 页面任务模型、单 DUT 边界、字段来源、插件与 Hub 契约、优先级和验收标准 | 确认 UI Schema 能力与版本、执行控制状态机 | “通用化必须把所有字段原样展示” |
| 软件工程工位与 Hub 维护者 | 表单组件、响应式布局、字段宽度、可选项机制、本地化路径、导航、错误定位、执行控制与状态一致性 | 实现有文档的通用编辑组件与可测能力声明 | “字段来自插件，所以页面体验不归平台” |
| 插件开发工位 | 业务字段名、单位、默认值、顺序、适用条件、规则目录、复位/采集/判定语义、数据迁移与执行正确性 | 提供 schema、UI 描述、结构化诊断、真实配置夹具 | “Hub 自动生成，所以无需设计配置体验” |
| 集成发布与验收 | 最终 EXE 加插件及配置的组合验证、版本/哈希绑定、真实长配置截图与任务测试 | 形成发行快照及可复核证据 | “源码测试过”“ZIP 可解压”“模拟 PASS” |

插件开发工位已经修改 `workspace.rs`，这部分仍属于 Hub 通用能力，应由 Hub 维护者完成契约审查和回归后接收。工位名称不改变模块所有权，也不应让两个工位同时重写同一渲染路径。

## 六 目标页面和字段设计

### 1 工作区结构

保留左侧测试项列表、中央配置工作区和右侧状态摘要。中央按业务节导航，默认只显示一节；右栏按“阻断问题—下一步—资源摘要—采集时序”排列，源码与诊断详情默认收起。窄屏将侧栏收进抽屉或页签，避免继续压缩中央区域。

中央编辑区采用明确的字段行布局：标签对齐，普通输入框高度统一；短字段使用受限宽度，文件路径使用完整字段行。建议普通字段宽度约 220—360 逻辑像素，中央表单在宽度足够时使用两列，具体阈值复用示波器页面约束并通过真实内容验证。避免每个字段无差别占满一整行。

九个现有数据分组可以保留以减少迁移，但视觉上应聚合为基本信息、设备与 DUT、固件、复位与采集、判定与 AI 等任务。不会为了合并页签而变更运行协议或丢弃字段。

### 2 DUT 和执行环境

配置保存产品型号、适用板卡版本及身份要求；本轮参数输入实际产品序列号和操作员。治具/工位可作为可选环境记录，不建立多工位管理入口。本轮实际身份以用户输入为准，配置约束不能静默覆盖输入；冲突通过预检提示。

同一 DUT 的多项配置不应要求用户重复录入实际身份。任何继承或默认值都应可见，并在报告中保存解析后的实际值。此项涉及现有配置来源规则，需要插件给出迁移方案，不能仅在 UI 隐藏重复字段后改变执行含义。

### 3 仪器绑定

每个角色用一张紧凑卡片，先显示是否需要该设备、设备类型和设备选择结果。日志卡片选择“普通 COM”后显示端口、波特率；选择“Dongle UART”后显示 Dongle、UART 通道和波特率。数据位、校验、停止位、流控按需要放入高级串口参数。

制造商、型号、资源地址等筛选条件不能默认和已选择设备并列铺陈。只有明确支持手动绑定或精确匹配的场景才展开。无需求的 bridge、DMM、load 不显示独立加号按钮，可归入“添加仪器角色”。

### 4 固件登记

当前版本支持 HEX/BIN 文件登记和校验，下载接口继续预留。常用区仅显示文件选择、格式、目标芯片；SHA256 由工具计算并可复制，作为校验信息展示。是否允许人工输入需明确业务用途，不能使显示值取代实际文件校验。

显示明确的“固件下载暂不支持”状态。下载专用基地址、写后 verify 等设置放入保留配置详情；旧配置若启用下载仍须预检阻断，不能通过禁用控件或隐藏字段悄悄清除。BIN 的有效性约束与未来下载参数应分清，暂不改变既有 schema 约束。

### 5 复位与采集

复位选择“DC 电源断电复位”或“WiParse Dongle 硬件复位”。前者只显示电源、通道、断电时长和释放确认；后者只显示 Dongle 与其支持的复位参数。固定 hardware、method、implementation 常量从普通界面移除。

页面固定说明：所有采集时点以复位释放确认后的 T0 为起点。用统一时间轴表达日志起点/时长、截图时点、可选源波形读取及预算。重叠任务在预检阻止执行，不提供并发采集选项。

### 6 判定规则

提供“规则摘要列表＋当前规则详情”。例如普通日志规则收起时显示“日志包含 AXI_LITE_OK，至少 1 次，必需”；否定正则规则显示“日志不允许匹配 FATAL/ASSERT/PANIC，必需”。原始 pattern 仍可查看和编辑，不伪造其含义。

核心编辑区只显示规则名、类型、匹配内容或指标/限值以及必需性。ID、证据引用、非默认匹配次数放入高级设置。类型使用中文显示名，内部枚举保留在数据中。组合逻辑显示全部满足/任一满足/取反及其子规则，空组合不能保存或运行。

限值可以立即修改使用，报告必须记录本次实际限值、单位、来源和快照；不引入当前范围之外的审批或电子签名流程。

### 7 AI 辅助

配置页只显示该测试是否使用 AI、允许输入的证据类型和相关用途；服务商、模型、API Key 统一进入全局设置并提供跳转。公网外发授权、脱敏与本地模型选择继续执行已有策略，不能为了精简界面省略外发状态。

AI 辅助结论与确定性规则结果分别展示，不能把模型建议直接提升为产品 PASS。具体 required AI 未完成时的处理，沿用插件规则契约并在预检说明。

## 七 整改任务和交付顺序

本报告用 R0 表示本次体验整改必须完成，R1 表示随后完善；它不同于旧综合评估中安全和正确性 P1/P2 的分级。

## 八 验收标准

### 页面和任务验收

1. 使用真实 FPGA 20 项配置作为主夹具；另外覆盖 0、5、500 项。500 项侧重容量和交互，不能代替复杂表单验收。
2. 至少覆盖 640、1100、1440、1920 逻辑像素宽度，明暗主题；中文完整检查，英文不得出现布局溢出。检查最终应用窗口含宿主工具栏、插件导航后的真实可用空间。
3. 逐一展开仪器绑定、普通 COM、Dongle UART、DC 复位、Dongle 复位、日志、截图与源波形、每类规则、AI 和固件保留配置。
4. 普通配置路径无 `selector`、`implementation`、`evidence refs`、`类型2`、原始 const 等未解释技术字段。高级诊断可保留原始键名。
5. 每个规则收起后可读出条件；非默认匹配次数可以配置；规则与采集引用可跳转，删除被引用项有明确提示。
6. 无不必要的水平滚动、重叠或信息裁切；长测试名可以省略显示但能查看全名。数字和单位相邻且无重复单位。
7. 用户可以完成“修改串口—切换复位方式—添加截图和源波形—设置日志规则及限值—保存—预检—运行—查看报告”，无需源码编辑。
8. 窄屏切换分组、存在未保存修改、预检错误定位、运行中只读、取消和返回均保留正确状态。
9. 上次 PASS 不能被误认为当前已修改配置已通过；预检失效原因与下一步明确。
10. 暂停展示等待安全边界与已暂停状态；停止后不能继续启动采集。按钮启用状态与真实 runner 一致。

### 发行验收

1. GUI、Hub、插件和样例冻结后统一验证，避免多个工位在打包中途继续改同一组文件。
2. 源码能力测试、视觉任务验收、模拟端到端和包完整性分别记录结果，不互相替代。
3. 记录 GUI EXE 哈希、插件版本/内容哈希、schema/UI 哈希和配置夹具哈希；最终截图必须来自该组合或明确标明源码审计帧。
4. 重新构建后不得复用旧 EXE 的验收结论。压缩后检查归档文件，不只检查源目录。
5. 打包校验脚本结果中的版本应从包中读取；当前 `verify-hub-package.py` 成功输出仍写死 `plugin_version: 0.3.1`，应修正，避免 0.4.0 验证显示旧版本。固定五项模拟断言也应与新版选用的演示夹具契约同步。
6. 当前旧包的通过记录只代表当时的包，不能在源码升级后直接拿当前源码对比失败来认定旧包损坏；应对照其冻结清单。

## 九 整改结论

本次反馈应登记为“FPGA 配置工作流与 Hub 表单体验整改”，不应仅登记为“FPGA 插件美化”。软件工程主责解决通用渲染机制；插件开发主责收敛业务字段与声明；系统架构主责明确契约和范围；集成发布主责对最终产物验收。

0.4.0 正在进行的卡片、导航、类型化规则和执行控制可继续复用，但现有规则页仍有明显冗余，不能宣布本轮 UI 已闭环。验收应以真实配置完成任务、最终 EXE 页面和证据绑定为准，再进行一次构建和打包。

本次输出整改报告，不改写其他工位正在开发的代码，不把开发过程中的阶段测试升级为正式验收结论。
