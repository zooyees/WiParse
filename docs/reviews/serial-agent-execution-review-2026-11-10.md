# 串口 AI Agent 执行链评审与整改

日期：2026-11-10。基线：`cursor/four-job-shell-and-marketplace`，WiParse 1.2.2，egui。

## 结论

截图暴露的是 Agent 执行架构缺陷，不能归咎于用户未提供日志或未反复确认。用户提出“分析本日志断充次数与原因”，已经授权对界面所选范围进行只读分析。宿主应主动取得证据，让模型识别实际格式、形成检索规则、调用本地引擎并给出可追溯结论。无需用户另行回答“开始扫描”“调用”“继续”。

本次整改覆盖串口专用入口及共用 AI 传输层，复用现有波形、计算和设备接口。没有依赖截图中的 708 行文件，没有把某产品的状态码或断充关键词写成通用判断标准。

## 根因及严重程度

|级别|原有问题|实际后果|本次处理|
|---|---|---|---|
|P0|工具定义只有提示词，没有服务商原生 function tools|模型说明应该调用什么，却不提交执行请求|Chat Completions 声明原生工具，保存 tool call ID 与对应结果；提供显式 JSON 兼容模式|
|P0|普通文字也被认作成功响应|“我还没读正文、请确认”被显示为分析完成|任务模式要求工具调用或结构化终结；允许一次自动协议修复，仍失败则明确任务失败|
|P0|首次请求只有统计元数据|模型没有可用于识别格式的证据，反复解释空字段|发送前后台扫描所选范围，提供分组、覆盖信息及有界样例；后续按需要继续取证|
|P1|最近 100 行的空样本字段混入手动全量分析|模型误把未上传全文理解成无法分析|手动上下文改为本地引擎语义，移除误导的空样本字段；自动监控采样另保留原行为|
|P1|只读分析与设备操作权限概念混淆|用户被要求开控制权限才能读取日志|所选范围只读分析自动执行，设备启停、命令仍检查权限及测试锁|
|P1|缺少任务状态、证据引用和无进展检测|计划、受理、完成混淆，重复扫描浪费资源|任务 ID、阶段、工具预算、实际证据 ID、重复读取检测及失效来源检查|
|P1|把报警行数当事件次数，缺少状态转换工具|重复报警造成重复计数，关联被当成原因|增加通用可配置状态转换提取，分别统计确认转换、初始断开、重复断开和歧义|
|P1|专用助手与平台专业能力割裂|无法核对现有波形、协议或工程计算结果|开放受限只读上下文、后台波形测量、协议报文及工程计算适配器|
|P2|输出大量内部预算、权限说明和空表格|回复冗长，用户无法获得所需结果|任务契约要求结论/表格优先、引用证据，简述实质不确定性，避免反复解释内部字段|

## 执行架构

1. 用户选范围、提出目标，创建绑定工程与来源的任务。
2. 本地引擎在后台读取所选范围，生成覆盖统计、分组和有限样例；原始全文不进入模型请求。
3. 模型识别字段、单位及状态含义，调用结构化搜索、分组、数值统计、上下文提取或状态转换工具。没有固定日志格式要求。
4. 宿主校验工具名称、参数、范围及权限，调用已有执行引擎，把实际结果附上证据 ID，继续同一任务。
5. 模型通过终结工具返回结果和证据 ID。宿主核对引用，界面保留可展开的实际工具活动；不会显示模型内部推理内容。
6. 只在证据不足以区分业务含义、缺少实际阈值或需要设备操作授权时询问用户。无有效工具调用时自动反馈一次协议纠错，不让用户充当调度器。

同范围后续提问保留最近三个工具结果作为历史证据；切换来源、范围或取消会阻止旧请求继续执行。历史证据不自动代表当前实时数据。

## 本地处理与专业判断

本地处理负责可验证的数据事实，模型负责推导规则和解释其适用性。支持文件清单、范围、包含/排除、正则、大小写、分组、数值统计、上下文及分页。状态转换工具的 active/inactive、实体、原因、时间正则由模型根据实际证据选择；数字状态、英文文本和结构化日志均可使用。

- 只对同一来源、同一实体已观察到 active 后的 inactive 计为确认转换。
- 初始 inactive 单独统计；重复 inactive 不算新事件；同时命中两个状态标记为歧义。
- 文件之间不拼接状态；事件包含来源、行号、原始时间文字、相邻关联观测。
- 邻近 UV/过温等日志只是关联证据，不能单凭邻近关系证明电气根因。模型应结合电压、温度、协议和时序实测核验。
- 总计数是所选规则在已覆盖范围内的计数，不等同于无条件的产品故障结论。日志淘汰、扫描未完成、实体预算或歧义必须披露。

不把“timeout”“fault”直接等同断充。若日志根本没有可辨识的充电状态，正确结果是说明已查范围和缺少的关键证据，而不是编造次数，也不是反复要求授权扫描。

## 平台嵌入范围

串口助手现在可只读查看波形、数据分析、测试报告、测试工作区、计算器、仪表上下文；可调用现有波形测量、协议帧和工程计算引擎。设备控制仍经过现有命令白名单、参数验证、授权、测试锁及实际作业完成查询，不开放 shell 或任意文件路径。

本次增加的原生便利工具 `wiparse_log_files`、`wiparse_log_analyze`、`wiparse_log_events` 都转换为已有 `log.files` / `log.analyze` 契约。MCP、CLI 和 GUI 使用相同本地处理能力，不复制产品解析逻辑。原有实时接收、日志行数限制、文件保存及本地预警流程不变。

## 服务兼容与资源控制

DeepSeek 官方说明以原生工具调用及对应 tool 结果续接对话；思考工具轮次要求保留 `reasoning_content`。本次传输保留这些字段但不展示内部推理。[DeepSeek 工具调用](https://api-docs.deepseek.com/guides/tool_calls/)、[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)。

千问不同模型对强制 `tool_choice` 的支持存在差异，因此使用 `auto`，由宿主检查并纠正无效执行响应，而非一律强制 required。[千问 function calling](https://help.aliyun.com/en/model-studio/qwen-function-calling)。

Chat Completions 的任务请求使用非流式原生工具；普通聊天原流式设置保留。Responses 及用户选择的 JSON 兼容模式保留结构化动作契约。网关不支持工具时报告诊断，用户可切换兼容模式；不会在 HTTP 请求失败后自动重发有副作用操作。

单任务最多 12 次模型工具动作、300 秒工作预算，已有本地扫描预算保留；连续原生对话保留完整匹配的工具轮次，并按轮次/字节裁剪。响应有界、事件分页、取消和来源校验避免无界资源增长。共享 AI 工作槽满时在本地排队，恢复后继续，无需用户重新发送；已经提交的网络请求不会因该机制重放。

## 验证与交付记录

本次使用本机模拟模型服务和合成日志，不使用用户特定日志、真实密钥或真实设备。关键端到端场景：只发送一次问题，模型先错误要求确认，宿主自动纠正，模型调用原生状态工具，实际本地引擎统计两次事件，最终结果引用真实宿主证据，全程没有第二次用户输入或设备授权。

同时检查：原生工具与显式 JSON 模式的请求差异、思考字段和工具 ID 续接、错误参数、范围/权限隔离、不同格式状态规则、重复报警、跨文件边界、分页和歧义；完整回归结果见 `docs/verification/serial-agent-20261110/verification.md`。

## 边界与后续方向

本次修复保证宿主执行闭环与证据获取，不保证任意模型都能正确理解任意私有固件日志。业务语义无法从证据推出时仍需澄清；用户不再承担常规只读工具的逐次确认。

离线全量分析与实时逐行预警是两个通路：本地规则负责即时告警，云端 AI 负责周期解释，不把模型响应速度当成实时安全联锁。未做真实付费 DeepSeek/千问账户与硬件组合验收，不宣称完成工业安全认证。后续可建立版本化固件字段词典、用户认可的领域规则及带标准答案的评测集；这些知识必须有来源与适用版本，不应以通用固定关键词替代实际证据。
