# WiParse Tauri + React/TypeScript 重构计划

状态：迁移开发中；2026-11-07已接手。执行边界以同目录交接报告R2为准。原方案中的全量独立服务为架构方向，不强制作为GUI迁移的预设前提。

## 1. 目标与范围

将 WiParse 的桌面界面逐步迁移到 Tauri 2 + React + TypeScript，形成统一、紧凑、可维护的研发测试工作台；保留并逐步抽离现有 Rust 核心、设备能力、Testing Hub 和插件协议。首期目标平台为 Windows x64，继续支持离线使用和现有部署路径。

交付范围包括：桌面外壳、设置与 AI、串口、仪器、波形、数据分析、集成测试、测试报告、计算器，及其运行、测试、打包、迁移与回退能力。界面迁移不自动等同于新增或完成无线充电测试能力。

既定产品约束：侧栏默认和最小宽度 200 逻辑像素（窗口极窄无法容纳时采用明确的折叠或滚动）；无多 DUT 工位并发；项目和配置可视化编辑；不以模拟结果冒充实机通过；保留项目、日志、原始波形、报告、配置与设备设置。

## 2. 当前事实与迁移边界

1. GUI 为 egui/eframe 0.31，见 `crates/wiparse-gui`；现有主题与布局不是一套可直接用于 Web 的组件库。
2. `wiparse-core` 包含可复用的核心能力，但设备和应用状态并未完全独立：`crates/wiparse-gui/src/backend/ui.rs` 的 `UiHost` 直接引用串口、仪器、测试等页面对象；`app.rs` 在 GUI 内创建并驱动这些对象和 API。
3. `wiparse-service` 是已有独立自动化服务，有本机 token、租约和作业账本；根据 `docs/AUTOMATION-SERVICE.md`，不能假设它已经覆盖全部现有 GUI 仪器、串口、FT4222 和 Testing Hub 功能。需要逐项清单和契约测试，不用新服务名称冒充现成功能。
4. Testing Hub 的 Node 运行器、配置文件、插件 `plugin.json`、数据目录和报告需兼容；FPGA 插件及无线插件都有视觉和仿真测试资产。无线 MT5788/FT4222 与恒流负载模式仍未完成实机验收；无线 20 项自动测试并未全部实现。
5. 现有部署包含 `D:\software\WiParse` 安装与工作区启动位置；必须识别用户真正启动的程序，禁止只更新一个副本却报告全部已更新。

## 3. 架构决定

### 3.1 目标进程与所有权

- React 负责显示、输入、虚拟列表、表单和用户交互；不得直接保存设备句柄、直接执行 SCPI/I2C、判定设备任务成功或伪造测试结论。
- Tauri 负责本地窗口、经过限制的命令桥接、原生文件对话框及进程生命周期；前端到后端使用版本化 DTO、结构化错误和能力发现。
- Rust 应用服务负责单实例设备会话、VISA、串口、Dongle/FT4222、采集和测试执行协调；重用 `wiparse-core`，按能力逐步从页面对象抽出。已有 Node 插件运行器以受控子进程接入，项目和证据仍以现有协议为准。
- 实际进程归属在 P0 的原型中确定：可以是 Tauri 宿主内单一 Rust 服务，也可以是独立服务进程；无论选型如何，一个工位同一时刻只有一个权威设备所有者。不得仅凭两套前端各自加锁宣称互斥。
- 过渡期保留旧 egui 版本作为回退；默认不同时启动两套设备拥有者。只读模拟原型可以并行；真实设备交接须停止测试、确认仪器任务结束、释放会话、验证所有权，再启动另一版本。

### 3.2 接口与数据

定义版本化命令和事件：`command_id`、`operation_id`、`run_id`、资源标识、时间与质量、结果状态、错误码、取消与超时；非幂等命令失败后不自动重发。前端断线不能改变任务真实状态，重连后通过快照与事件序号恢复。高频数据由 Rust 侧缓冲、分页、限流/背压；前端按可见区获取日志及波形多分辨率数据，不能把完整原始数据反复转换成 JSON。Tauri 支持命令、二进制响应与通道，但实际吞吐必须按本项目测试：[Tauri 调用 Rust](https://v2.tauri.app/develop/calling-rust/)。

测试配置、运行快照和报告结果分离；判定结果与执行状态分别记录。时序保留现有业务约束：FPGA 采集以复位释放确认后的 T0 计时；MT5788 必须先从本轮 TX 日志确认 RX 已工作，再通过 WiParse FT4222 的 I2C 访问；固件 HEX/BIN 下载仍为预留接口，不冒充已实现。物理输出状态无法确认时保留恢复状态，不自动重试。

### 3.3 安全与分发

使用本地资源、限制 WebView 内容来源和 Tauri capabilities，配置 CSP，不将任意文件或插件当成可执行 Web 内容；注册命令还需后端逐项鉴权、输入验证与资源范围检查，不能仅依赖窗口权限。日志、报告、设备返回内容按不可信文本显示；AI 外发遵守现有用户确认的策略。Tauri 的 [CSP](https://v2.tauri.app/security/csp/) 与 [运行时权限](https://v2.tauri.app/security/runtime-authority/) 是基础配置，不代替应用层设备授权。

Windows 交付同时设计便携包和安装包，验证无网络安装、WebView2 缺失/版本不匹配、VISA、LibFT4222、Node、VC++ 和符号文件；是否使用离线安装器或固定运行时由首期部署测试决定。[Tauri Windows 安装说明](https://v2.tauri.app/distribute/windows-installer/)

## 4. 设计规范与界面验收

先产出可点击原型，再实现组件；不以换主题颜色代替流程设计。统一标题、输入、按钮、表格、状态、空态、错误、选中和焦点；全局提供深浅主题与中文、英文。默认控件高度 28 逻辑像素，面板间距目标 6、窗口外边距目标 4；如碰到可读性、触控或极窄窗口冲突，以实际验证调整，不盲目强制所有元素同尺寸。

每页明确：主要任务、首要操作、常用配置、次要/高级设置、预检错误、运行中、停止、结果及证据。测试矩阵中勾选运行与选中查看分开，状态至少支持 TBT、TESTING、PASS、FAIL，并保留中止、错误和无法判定的真实语义。限制在报告中显示，允许即时修改，不引入用户未要求的审批或电子签名。

测试视图覆盖 1100×720、1440×900、1920×1080、100%/125%/150% DPI、中英文、深浅色；再用真实用户显示器检查截图标注的顶部、左右与底部留白。覆盖空状态、已加载配置、运行、错误、长名称、设备断线；不依赖单张空页面证明完成。滚动、聚焦、键盘、缩放及可访问名称至少满足常用操作。

## 7. 性能、测试与交付标准

- P0 先测旧版和参考机：冷/热启动，20/500 项加载与搜索，串口持续写入/滚动，典型及大波形缩放，内存、CPU、事件丢失、设备断线恢复。每项记录测试数据规模、硬件、采样时间和 p50/p95。正式数值以 P0 基线和产品要求确认；没有实测不得宣称更快。
- 目标：500 项不需要一次渲染全部行；日志持久化不随界面刷新丢数据；波形交互只请求可见区或适当层级数据；长操作不阻塞停止；所有操作在已确认的硬件安全时序内完成。超出基线的性能退化须定位并处理或明确延期。
- 自动检查：Rust 单元与契约、前端类型/组件/状态、Node 运行器、跨进程取消和重连、保存冲突、文件越界、恶意日志/报告、构建产物完整性。测试必须覆盖实际用户行为和故障，不以截图无崩溃作为完成。
- 真实工位验收：分别列出 MDO3014、RIGOL 832、FT4222 + MT5788、可配置电子负载、TX 串口；记录实际连接、参数、结果和证据；产品限值由界面输入，不预设或虚构。模拟通过和实机通过分开。
- 发布前同时校验新包、覆盖后的 `D:\software\WiParse` 和实际启动的可执行文件哈希；保留用户配置、工程与日志；部署发生异常时恢复备份，禁止删除未备份的数据。新旧数据格式若无法双向兼容，先只读预览与复制迁移，验证回退前不覆盖原数据。

## 8. 进度与投入估算

以下仅为规划级估算，不是承诺：假设 2 名熟悉 Rust/设备的工程师、2 名前端工程师、1 名测试工程师及部分时间的设计/发布支持，工位和仪器可用，P0～P4 的可评审原型约 6～10 周；覆盖全部页面、兼容与实机验收约 14～24 周。实际取决于 GUI 耦合拆分、波形数据规模、硬件可用性和验收反馈。P0 结束后按实际清单和基线重新估算；可并行工作必须满足接口冻结和单一负责人原则。

## 9. 当前待确认项与默认决策

- 组件库与图形库：P1 以 React/TypeScript 为方向，在原型阶段依据中文、深浅主题、虚拟列表、许可及离线要求选择并锁版本；不提前把未测库写成已选型。
- 进程部署：P2/P3 用功能和故障验证确定进程内服务或独立进程；过渡期不得双重设备控制。
- 新旧切换：优先独立安装目录和同一份只读/复制数据演练；最终原位替换须完成备份及回退验收。
- 无线产品限值、仪器连接、串口波特率均由 WiParse 参数配置；无需把它们写死在此计划。实机联调依赖设备到位和可配置界面，而不是虚构数值。
- 本计划不批准忽略现有未提交修改或删除旧目录；后续实施前应重新核对工作区状态。
