# WiParse 硬件测试与数据分析 Agent 开发计划

2026-11-11，供产品、软件、插件、Dongle 和测试工位排期。基于 WiParse 1.2.2 egui 当前工作树。以下指标与工期为建议目标，第一阶段采集基线后冻结。首期范围为无线充电研发验证，随后用不同产品的数据验证可移植性。

## 首个交付场景

工程师选择一次测试，输入“找出本轮异常断充，画出事发前后的 VIN、VBRG、功率，标出对应协议帧，形成报告”。交付物为事件清单、数据分析页内可缩放的曲线、跳转到原始采样和日志的证据、可重新打开的 Markdown 报告。报告分开记录实测事实、候选原因、反证和下一项最有区分度的测量。正常结束充电、设备拔出、适配器重协商、接收端主动停充须能区分。缺少信号时指出缺哪个通道、哪段时间；仅在确实需要重新采集时提出设备操作。

首版同时走通两条路径。离线模式用已有文件完成取证和解释。在线模式用本地规则侦测事件、冻结预触发数据，随后由 Agent 调查。分别计量事件到冻结、冻结到首条有效证据、证据到报告的时延。快速捕获和保护由本地系统承担。

## 排期、责任和验收

建议按两名软件工程师、一名插件/算法工程师、一名验证工程师排期，Dongle 与硬件负责人配合联调。预计 12 周交付候选版。真机进度取决于一套可控 DUT、已验证示波器、源/RX、同步条件和故障样本能否按时到位。

| 阶段 | 牵头 | 工作包与交付 | 阶段退出条件 |
|---|---|---|---|
| 第 1–2 周，建立基线 | 测试、架构 | 冻结任务集、测量容差、任务和证据契约。记录当前版本的一次成功率、人工介入、错误归因、时延及用量。修复复合请求中局部否定导致整句跳过目标登记的问题。 | “不要摘要，算时长、画曲线、存报告”登记三项交付。中文同义表达、单目标、追加与撤销目标均有回归。评测输入、标准答案和工具权限可复现。 |
| 第 3–4 周，统一任务执行 | 软件平台 | 在现有 Rust 工作流上抽取公共执行状态。串口与共享助手先迁移只读任务。GUI 展示待办、正在执行、已验证、缺证据和失败原因。区分排队与纠正当前任务。 | 从两个入口运行同一案例得到等价交付。重复只读确认 0 次；取消、换源和晚到结果不能污染新任务。 |
| 第 5–6 周，全量数据到报告 | 数据分析、插件 | 泛化字段与分帧规则，支持日志、表格、采样与协议帧的源引用。统一单位、缺失值、时钟域和时间窗。复用本地提取、历史存储、绘图和报告服务。 | 百万行样本中的单次异常可定位；图、CSV、AI 统计和报告的原始行号或采样点一致。无同步锚点时不能输出确定的跨设备先后结论。交付首个离线可试用版。 |
| 第 7–8 周，断点恢复与仪器执行 | 软件平台、设备服务、Dongle | 项目内持久化任务、证据索引、命令状态和产物；按设备能力预检。接入首套示波器、源及可用 Dongle 接口。分开记录命令接受、设备读回及数据获取。 | 注入超时、应用重启、USB 重插、返回延迟及丢样。恢复后从最后已验证步骤继续。结果未知的写命令须先读回或转人工；故障测试中重复施加刺激 0 次。 |
| 第 9–10 周，领域诊断与监控 | 插件、算法、测试 | 交付充电状态/断充、VIN/VBRG 控制、PING/工作频率、死区、输入协议/Qi 通信质量的分析配方；增加适配器兼容矩阵和批次差异。每个配方声明前提、信号、算法、误差、反例、证据和缺测处理。 | 用金样、故障注入和证据不足案例盲评。死区要求实际同步栅极波形及探头时延校正；通信质量分别记录输入协议与 Qi 并注明计数分母。缺必需数据不能判 PASS。 |
| 第 11–12 周，真机与对标 | 验证、质量 | 比较现版、候选版、通用 Agent 接同一工具集和人工参考流程。执行长稳、断线恢复、双模型回放。交付 EXE、版本/能力矩阵、基准结果和回退说明。 | 冻结盲测集与统计口径；现场限值由产品与质量负责人批准。没有设备或同步条件的测试标记缺测。候选版与工业批准分别记录。 |

## 软件、插件与设备的接口

- 平台维护任务状态、授权、证据索引、跨页显示和通用算法。任务记录目标、输入范围、验收条件、预算、未决问题、工具版本、来源绑定及交付物。证据保存相对工程的文件引用、内容指纹、行/帧/采样区间、规则版本和覆盖状态。大数据集通过本地句柄读取。任务事件和检查点写入项目数据库；重开工程后验证文件指纹和设备身份。
- 工具按发现、读取、计算、呈现、产生副作用分类，描述参数、单位、读回方式、失效条件和取消能力。相互独立的读取可以并发。只在有新证据、覆盖范围扩大或交付状态变化时继续投入预算；无进展时优先换方法，并返回已完成部分。
- 产品插件维护状态机、产品限值、兼容矩阵、测试编排与正式判定。Agent 可生成待审的测试草稿、调用批准的配方、提出补测及解释判定。批准一次有明确设备、范围、期限的测试配方；范围外的动作单独确认。
- Dongle 提供 UART/I²C、IO 事件、时间戳、溢出和健康状态；DAP 能力按设备契约使用。示波器负责模拟波形。工位负责独立保护、校准、接线和参考仪器。各接口以能力探测结果为准。契约变更同步更新模拟器、旧版本兼容测试及插件 SDK。
- 优先复用现有 workflow、共享 Session、串口 Run、data.extract/data.present、日志扫描和报告读取。执行记录先以旁路方式与旧版比对，再按入口启用。异常时切回原入口，仍可打开原工程、数据和报告。保留 DeepSeek/千问兼容适配，实际模型单独计分。

## 如何证明领域领先

首轮建议建立 60 个独立任务，五类任务各 12 个，每类覆盖正常、故障、证据不足情形。按产品型号、固件版本和采集批次隔离开发集与隐藏集。同一记录的改写问法用于语言鲁棒性测试，不重复计作独立硬件案例。初始 60 项用来定位问题；对外比较前扩大盲测，报告样本数、置信区间及典型失败，不用单个演示推断行业排名。

| 指标 | 计算口径与候选版建议门槛 |
|---|---|
| 一次请求正确交付率 | 全部指定产物可打开、数值在冻结容差内、证据可定位、无需用户再催，才算成功。隐藏集目标 ≥90%，同时单列每类任务成绩。 |
| 根因与证据 | 分别统计已知根因命中率、排除正常停充的误报率、证据不足时正确保留结论的比例。缺测误判 PASS、编造证据、越权执行作为发布阻断项，报告实际分母。 |
| 效率与成本 | 累加成功、失败、修复和重试所用 Token，再除以正确交付数。同时给出 P50/P95 时延、人工分钟数和缺失 usage 比例。首轮优化目标为同质量下每次正确交付 Token 较现版下降 25%。 |
| 实时性与恢复 | 由工位预先给出触发时间预算和允许盲区。测事件到冻结 P95、丢样率、命令未知状态处理、恢复后重复操作。测试中必须能定位每个缺口。 |
| 对标公平性 | 系统对比使用相同数据、WiParse 工具接口、可执行动作、限值与专家评分。可统一模型时另测同模型运行时；无法统一时标明模型、版本和预算。由未参与实现的工程师盲评。只对实际验证的任务和设备范围给出领先结论。 |

## 前两周可直接认领的工作

1. 测试负责人先做 12 个种子案例，保留原文件、故障注入记录、专家答案、容差与允许的“不足以判断”答案。首先覆盖断充、跨时钟误判、含局部否定的组合请求。
2. 平台负责人给现有任务轨迹补齐请求、目标、执行结果和产物的关联，输出逐任务对照表。用已有回放工具复现一次遗漏目标；同时测当前两种模型的真实表现。
3. 数据负责人从原日志走通一份可点击回源的基准报告，逐项核对时间窗、单位、曲线和报告文件，作为以后每周可重跑的验收样本。
4. 插件与工位负责人冻结第一套 DUT、设备、通道、固件和限值；Dongle 不齐时先用记录回放，真机里程碑保留独立状态。
5. 第 2 周评审只看三份交付：可重放的基准任务、逐项结果与失败原因、第一条端到端演示。按实际瓶颈决定第 3 周的资源分配。
