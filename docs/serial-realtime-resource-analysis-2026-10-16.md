# WiParse 串口实时接收资源分析与优化方案

1.1.32 更新：固定休眠、空闲重绘、最大行宽维护、附加串口消费预算及滚轮历史查看已进行增量落实，见 [全功能检查与落实报告](system-audit-1.1.32-2026-10-16.md)。下文保留 1.1.31 基线和原始架构评估；完整后台写盘和会话处理器替换未纳入本次实现。

分析对象为 WiParse 1.1.31 Windows Release。结论是：可以保留现有功能、显示行数限制和用户参数，通过调整数据流、后台处理和绘制调度降低资源占用并改善响应。优先解除接收线程的固定休眠限制，再隔离主线程耗时工作，最后优化缓存和绘制。只降低界面刷新频率会掩盖吞吐不足，不能解决问题。

本文为代码审查、短时基线测量和待实施方案。串口架构及滚动行为尚未按本方案修改；1.1.31 安装包包含此前完成的仪表界面与报告调整。

## 当前数据流

```text
串口 COM 或 Dongle WinUSB 或 TCP
  → SerialSession 读取和分行、识别指标帧
  → serial_worker 添加显示时间戳
  → 8192 条有界事件队列
  → GUI 主线程每帧消费最多 400 个事件，取队列阶段最多 4 ms
  → 简报与测试事件处理、测试证据写入、事件总线发布、日志写盘
  → 5000 行显示 FIFO、筛选索引、可见行绘制
```

已有合理基础：独立读取线程、有界接收队列、64 KiB 文件缓冲、5 秒定时 flush、日志可见行虚拟绘制、只在串口页面可见时增量维护实时筛选，以及后台读取文件。这些能力应保留。

## 本机短时测量

使用当前 Release GUI、本机 TCP 串口模拟、隔离配置与日志目录；不连接物理设备。每行包含约 128 字节原始文本，GUI 继续执行原有时间戳、保存和事件处理。普通场景预热 1 秒后采样约 8 秒，超限场景采样约 16 秒，每秒调用一次需要主线程处理的状态 API。程序窗口通过隐藏启动选项运行，因此结果不能替代用户前台操作的帧时间测试。

本机有 16 个逻辑处理器。下表 CPU 是整个进程相对整机的占比；括号为相对一个逻辑核的占比。内存为整个 GUI 进程工作集，含图形、字体和其余工具基础开销，不能全部归因于串口。资源测试期间有本机打包任务，数据用于识别量级和瓶颈，不作为精确性能承诺。

| --- | --- | --- | --- | --- |
| 未启动接收 | 0.36%（5.75% 单核） | 181.2 | 20.3 / 21.6 | 0 / 0 |
| 已连接但无数据 | 1.62%（25.87% 单核） | 184.2 | 7.9 / 33.0 | 0 / 0 |

发送数为发送线程已完成 socket 写入的行数，接收数为取样时 GUI 日志的绝对累计数。不同读取时刻会产生小差值。2000 行场景的巨大差值表明链路积压；不能把差值直接判定为丢失，也不能用稳定 CPU 或较快状态 API 宣称接收正常。超限场景仍只显示 5000 行，验证了原有限制生效。

API 往返延迟并非鼠标响应时间或接收至屏幕呈现的延迟；本次没有逐帧或 GPU 性能采集。短时间内内存变化包含启动后缓存回收，不足以证明存在或不存在长期泄漏。

## 代码确认的问题

### 接收线程存在固定吞吐限制

`crates/wiparse-core/src/serial.rs` 的 `SerialSession::poll_events` 每次最多读取 2048 字节。`crates/wiparse-gui/src/serial_tool.rs` 的 `serial_worker` 每次调用后固定休眠 20 ms。仅按休眠计算，连续流的理论上限约为 102400 字节每秒，实际还需扣除读、解析和调度时间。

2 Mbaud、8N1 的线路净字节率约为 200000 字节每秒，超过上述上限。Windows 驱动、设备缓冲或 TCP 缓冲可以暂存积压，但不能修正持续吞吐不匹配。实测高负载 GUI 入库速度与此限制相符。

读取无数据时已经由 50 ms 超时等待，继续固定休眠还会增加数据和发送命令的等待时间。队列满时 `tx.send` 阻塞读取线程，UI 的处理速度会反向影响底层接收；物理串口不能依赖 TCP 那样的背压避免丢数据。

### 主线程预算未覆盖全部接收工作

`drain_events_with_bus` 的 4 ms 预算只覆盖取队列环节。之后的 `ingest_live_batch`、测试证据处理、逐行事件发布、文件写入、FIFO 更新和筛选都在预算之外。64 KiB 缓冲减少系统写入次数，但缓冲用满、定时 flush、磁盘拥塞时，主线程仍可能等待实际 I/O。

附加串口 `drain_extras` 会一直读取到队列暂时为空，没有与主串口一致的行数或时间预算。多个来源持续输入时，某个来源可能长时间占用一帧。

测试运行时 `tick_test` 每次会构建最近最多 5000 行的字符串列表。应核对测试步骤真正需要的数据，避免在没有新输入或无关步骤中反复复制完整窗口。

### 缓存满后的维护成本增加

`LiveLogStore::append_lines` 在淘汰行长度等于当前最大行长度时，会重新扫描保留的全部行并计算字符数。等长日志很常见，因此满 5000 行后可能每个输入批次都触发扫描，而不仅是偶发的最长行淘汰。

`shift_after_front_eviction` 会为每个窗格移动行号，过滤并重建查找命中和行映射；`append_live_filter_matches` 每批重新准备筛选模式，并重新生成命中行映射。分屏、密集命中和频繁淘汰叠加时会增加分配与遍历开销。

目前 `String` 进入缓存时重新构造 `Arc<str>`；显示、事件 JSON、测试证据和 API 返回还会按各自需求复制或序列化文本。现有 `Arc` 能作为减少重复拷贝的基础。

### 无新数据时仍进行周期性绘制

`crates/wiparse-gui/src/app.rs` 只要正在监控且串口页面可见，就请求约 33 ms 后重绘；切换其他工具后通常为 500 ms。已连接无数据与未监控场景的 CPU 差异，以及可见与后台场景的差异，都支持优先调整这一环节。

日志已经只绘制可见行，不需要重写为另一套虚拟列表。`layout_log_line` 每次绘制仍构造文本；egui 本身有字体布局缓存，应先测量缓存命中和临时分配，再决定是否增加缓存。不可长期跨字体图集变动保留过期 Galley，避免引入显示错误。

### 行数限制不等于全部内存都有上限

5000 行 FIFO 和 8192 条事件队列限制的是条数。`SerialSession.buf` 在持续没有换行时会增长，重复从头扫描还会使累计扫描成本增加。极长单行同样会占用大量内存。不能为降低占用而默默截断数据；应以分块扫描、共享块及必要时临时文件承载保留完整数据。发送队列当前为无界队列，也需纳入异常发送负载检查。

## 推荐的数据流调整

```text
每个输入源的 I/O 工作线程
  → 按原有协议完整读取、记录接收顺序和元数据
  → 有界的共享日志批次与明确的过载状态
  → 后台会话处理器
      → 顺序日志保存与测试证据写入
      → 简报、指标及测试状态计算
      → 保持原有逐行语义的 API 事件
      → 5000 行显示视图及增量筛选索引
  → GUI 只消费结果快照、导航状态和交互命令
```

不必为每一项处理都创建线程。建议先保留每端口 I/O 线程，增加一个负责顺序处理和写盘的会话工作线程。避免过度拆分引入锁竞争和乱序。命令发送、停止、异常和 flush 确认必须有明确优先级与返回状态。

1. **持续读取替代固定休眠。** 无数据时阻塞等待，有积压时按可取消的读取批次持续处理；发送命令和停止信号在批次边界检查。保留波特率、行格式和协议语义。先验证 COM、TCP、WinUSB 三条路径，不能只优化 TCP。
2. **按批次传递共享日志。** 批次中每行保留顺序及原有显示文本；对内共享 `Arc`，对外仍保持现有 API 和事件格式。批次传输时仍按原有行数容量核算，不能把 8192 条变成 8192 个任意大批次。
3. **后台写盘与测试处理。** 保留文件内容、命名、BOM、顺序和 5 秒 flush 行为；停止、切换文件、导出和退出时确认尾部提交。磁盘满和写入失败仍必须进入界面及测试状态，不能因异步化而静默失败。测试超时使用单调时钟，不能以绘制频率作为时钟。
4. **主线程统一调度。** 主、附加来源共享公平的调度预算；保留已有 400 条和 4 ms 参数，避免只限制取队列而留下大段无预算后处理。后台工作不依赖主线程重绘来继续运行。
5. **改用绝对行序号维护索引。** 利用已有 `dropped + window index` 序号，淘汰只推进基准和移除过期前缀；显示时转换为当前相对位置。筛选模式只在模式或大小写设置变化时编译，新增行只维护新增命中。
6. **增量维护最大行宽。** 入库时缓存字符数，使用带绝对序号的单调队列维护窗口最大值，避免等长日志在每批淘汰后全窗口扫描。字体、窗口和主题改变仍触发必要布局更新。
7. **按变化请求绘制。** 输入到达时合并唤醒；有新可见数据、交互、状态变化或动画时才绘制。保留正常实时状态下的流畅显示节奏，历史查看时只更新必要状态提示。后台数据处理和报警持续运行，不能随着页面隐藏而变慢。
8. **减少重复解析和事件分配。** 指标帧已经在接收层解析，可以沿链路传递解析结果，避免重新把格式化文本解析为指标。简报的 Qi 统计属于现有功能，不能因关闭悬停自动解析而停用。事件总线即使没有订阅者也保留 512 条历史语义；可共享不可变事件或按需序列化，不能直接省略发布。

上述方案预计改善吞吐、主线程阻塞和空闲 CPU，但具体降幅必须通过改造前后的同条件对照确认。共享日志减少拷贝并不意味着所有文本和图形内存会同比下降。

## 滚轮历史查看方案

当前 `log_view.rs` 检测到任意滚动就取消 `scroll_pinned`，没有限定在日志视口内；随后只要距底部不到约 1.5 行，又会自动设回跟随。满窗口时底层 FIFO 仍不断淘汰，虽然选择、查找等行号进行了平移，滚动像素位置和所显示的内容没有被固定。这是“向上滚动仍刷新”的两项代码原因。

采用显式状态 `FollowLatest` 与 `ReviewHistory`：

| 操作或事件 | 行为 |
| --- | --- |
| 日志视口内首次向上滚轮，且不是 Ctrl 缩放 | 处理当前帧滚动前进入历史状态，固定当时的有界日志视图，然后执行滚动 |
| 历史状态继续滚动、拖动滑块、选择、复制、查找 | 在同一份上下文中正常操作，不被新日志或 FIFO 淘汰改变 |
| 新日志到达 | 正常接收、保存、解析、测试和告警；历史正文保持不变，可显示新增数量 |
| 滚轮向下到历史底部 | 保持历史状态，不隐式恢复实时跟随 |
| 点击右侧滚动条底部向下三角 | 释放历史视图，清除过期定位保持与高亮跳转，跳到最新位置，并恢复跟随 |
| 清空日志或开启新会话 | 清除旧历史快照和选择，按清空或新会话语义初始化 |
| 切换工具再返回 | 保留原历史查看状态；后台接收不停止 |

底部三角需要作为“到最新并恢复跟随”的明确命令接入，必要时增加贴合现有滚动条的专用按钮。当前此日志路径未发现独立的底部三角处理器，不能仅依赖滚动控件内部到达底部的判断。

固定历史视图可共享当时最多 5000 行的 `Arc`，每个会话共享一份、各窗格保存独立导航。这样实时 FIFO 和历史视图各自不超过原有行数上限；但当实时窗口完全更替后，历史视图会额外保留旧文本，因此总内存仍可能增加，不能宣称零额外内存。长期或极长日志如需严格控制额外内存，可采用文件支持的历史视图；未启用保存时不能假定磁盘已有完整原文。

## 实施顺序与验收

第一阶段处理固定休眠、主线程 I/O 和多来源调度，建立接收、解析、写盘、GUI 应用四个累计序号及积压观测。第二阶段完成历史视图及底部按钮，改进淘汰索引和行宽维护。第三阶段再按性能分析结果优化绘制缓存、事件序列化和分配。

保持现有功能需要逐项验证：文件字节内容及顺序、指标和 Qi 简报、筛选与查找、分屏选择复制、API 分页和事件回放、测试判定及证据、数据分析实时输入、多端口、停止恢复、退出尾部写入。不能用抽样日志、跳过解析、丢弃事件或增加缓存上限换取性能。

建议使用以下目标作为后续验收门槛，尚非当前版本实测承诺：

- 在 115200、1 Mbaud、2 Mbaud 的等效字节负载下进行 COM、TCP、WinUSB 对照；明确行长和突发量，不能仅报行数。
- 连续至少 30 分钟及 8 小时长稳测试；超过 5000 行后循环淘汰，检查内存是否趋稳、序号是否连续、录制内容是否完整。
- 输入稳定低于支持吞吐时，积压应在突发后回落；持续超过能力时明确提示积压或溢出，物理设备是否有流控必须纳入结论。有限缓冲不能对无限过载承诺零丢失。
- 与同机同负载基线比较 CPU、工作集、私有提交、分配、线程唤醒、磁盘写入、队列深度和积压时长；区分显示页、后台页、历史查看、开启测试、密集筛选及多端口。
- 前台输入响应 P95 目标小于 50 ms，持续流数据显示延迟 P95 目标小于 100 ms，常用交互期间避免主线程连续阻塞超过 100 ms。需要新埋点与前台帧时间采样验证，不能由本次状态 API 延迟代替。
- 历史查看在持续输入并淘汰多个完整窗口后，首行内容、选择和查找结果仍稳定；点击底部三角一次即回到最新并继续跟随。日志区之外滚轮、Ctrl 缩放不能误触发暂停。
- 覆盖磁盘慢、磁盘满、设备断开、长时间无换行、超长行、写队列拥塞、切换文件及退出；错误必须可定位到来源，不能让后台线程静默停止。

本次实际结果支持开展有针对性的渐进重构，不支持承诺某个固定百分比的资源下降，也不足以给出长期内存泄漏或物理串口不丢包的结论。
